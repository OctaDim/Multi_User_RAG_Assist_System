## Полное поручение пользователя

Оформи заявку harness на изменение политики частоты Git-коммитов для всех видов
работы и всех этапов задачи: ideate, brainstorm, планирование, реализация,
проверка, исправления и документирование.

Проблема: сейчас отдельный ответ пользователя или небольшое уточнение трактуется
как завершённый этап и вызывает коммит. Это создаёт множество мелких коммитов
вместо понятной истории задач и результатов.

Требуемая политика:

1. Единица коммита — завершённая задача или содержательный подэтап с
   самостоятельным, проверенным результатом. Ответ пользователя, отдельный
   вопрос, ход диалога или небольшая правка сами по себе не являются границей
   этапа.
2. Связанные небольшие изменения накапливаются и сохраняются одним коммитом
   после завершения соответствующего подэтапа. Документы, решения и память
   обновляются своевременно, без обязательного коммита после каждого обновления.
3. Для короткой задачи обычно достаточно одного итогового коммита. Для
   длительной задачи допустимы промежуточные коммиты после логически завершённых
   частей. Не устанавливать механические пороги по числу вопросов, файлов,
   строк или минут.
4. Исключения: явное поручение пользователя сделать коммит сейчас либо
   обоснованная необходимость сохранить промежуточный результат перед рискованной
   операцией. Объяснять причину такого исключения.
5. Перед коммитом выполнять проверки, соответствующие изменению. Не включать
   посторонние изменения и не создавать пустые коммиты. Эта политика не даёт
   дополнительного разрешения на push, PR или merge.

Найди все канонические правила и навыки, задающие частоту коммитов, включая
comm-commit-task-stages. В заявке перечисли затрагиваемые источники и предложи
согласованные изменения, устраняющие требование коммитить каждый небольшой шаг.

Добавь критерии проверки: серия уточнений brainstorm не создаёт коммиты на каждый
ответ; несколько связанных исправлений образуют один коммит; завершённые
самостоятельные этапы сохраняются отдельно; явная команда пользователя на
коммит выполняется.

## Область и найденная причина

Это изменение переносимого механизма common, поэтому заявка размещена в
common/inbox. Оно применяется ко всем проектам, видам работы и выбранным
маршрутам, включая самостоятельное выполнение.

Поиск текущих canonical rules/skills/base и остальных машинных материалов
common/project, а также установленных проектных копий нашёл одного владельца
частоты: [comm-commit-task-stages](../../skills/comm-commit-task-stages/SKILL.md).
В проектном пакете отдельного владельца нет. В действующих common rules нет
самостоятельного требования частых коммитов. Карта источников, строки,
состояние копий и внешние требования приведены в [sources.md](sources.md).

Владелец требует коммит перед набором/каждой задачей, после каждого завершённого
этапа и в конце. Определения содержательного этапа нет. Это допускает слишком
мелкую интерпретацию границ; установленные SP/AS-навыки дополнительно требуют
частых коммитов или коммита каждого инкремента. Сам CE brainstorm не требует
коммита каждого ответа. Указанная пользователем проблема принимается как
наблюдение; причинность каждого старого коммита по одному git log не доказана.

Предыдущая заявка [2026-10-10-task-stage-commits](../2026-10-10-task-stage-commits/request.md)
завершена и отражает прежнее поручение. Её исходные требования, результаты и
свидетельства сохраняются как история; новая политика предлагается этой заявкой.

## Согласованные изменения

1. Заменить тело и уточнить trigger существующего `comm-commit-task-stages`.
   Убрать автоматический коммит при входе в задачу/набор и при каждом формально
   названном шаге. Единственная общая единица — завершённый проверенный результат.
   Начало новой задачи само по себе не превращает прежние незавершённые правки
   в разрешённый коммит.
2. Считать подэтап завершённым, когда его отдельный результат можно описать,
   проверить подходящим способом и использовать/рассмотреть самостоятельно.
   Имя фазы, чекбокс, ответ пользователя, успешный тест после очередной малой
   правки или сохранение файла недостаточны. Уточнения внутри brainstorm и
   связанные исправления накапливаются до завершения соответствующего результата.
   Самостоятельный завершённый результат ideate, согласованный документ требований,
   проверенный план, реализованная часть или итоговый отчёт могут быть границами.
3. Документы, решения, результаты проверок и память обновлять своевременно в
   разрешённых категориях harness; обновление не требует немедленного коммита.
   Для короткой задачи обычно один итоговый коммит. Длительную задачу делить по
   самостоятельным результатам, без лимитов вопросов, файлов, строк или времени.
4. Добавить [короткое правило](candidate/harness/common/rules/comm-commit-result-boundaries.md)
   перед выбором процедуры. Обоснование нового always-loaded guard: внешний
   workflow может потребовать коммит до выбора навыка границ. Правило направляет
   в одного владельца и устанавливает приоритет частоты; алгоритм не дублирует.
   Нового Git-навыка, хука, счётчика или настройщика порогов не создавать.
5. Частоту из SP/CE/AS применять через общего владельца. На будущее формулировки
   «Frequent commits», «commit each increment», commit после каждого шага плана
   и каждого раунда исправлений означают только границы самостоятельных результатов.
   Согласования, проверки, изоляция, безопасность, ownership, exclude и правила
   выбора исполнителя сохраняются. Внешние plugin cache в этой заявке не править:
   локальное canonical правило задаёт согласованную политику для их применения;
   карта конкретных адаптаций находится в sources.md.
6. Не обходить механизмы, которым коммит необходим для безопасного восстановления
   или передачи. Группировать связанные малые шаги в единицу результата до запуска
   таких механизмов. Если нужен промежуточный коммит перед риском потери/смешения
   результата, назвать конкретную операцию и причину исключения. Синтетический
   transport commit в отдельной изоляции не является разрешением дробить историю
   канонической ветки. Если безопасное группирование невозможно, согласовать
   конфликт до зависимой операции; не выключать проверки контроллера.
7. Выполнять явную команду «сделай коммит сейчас» как исключение из ожидания
   границы, объяснив её основание. Проверки, ownership и запрет пустых коммитов
   действуют и в исключении; незавершённый результат обозначать честно.
8. До любого коммита проверить актуальные изменения соответствующим способом.
   Для документов — целостность требований, непротиворечивость, ссылки; для кода
   — релевантные проверки. Не выдавать незапущенные/неуспешные проверки за успех.
   Коммитить только принадлежащие задаче разрешённые изменения по ce-commit,
   сохраняя посторонние staged/unstaged/untracked и exclude. Пустые/повторные
   коммиты запрещены. Push, PR, merge и переписывание истории отдельно разрешаются.

## Критерии будущей проверки

Проверять по transcript/tool calls и фактическим HEAD/index/diff, а не только по
словам агента. Для каждого сценария фиксировать исходное состояние, изменения,
проверки, причины границ/исключений и созданные хеши. Объём примеров — тестовые
данные, а не механические пороги политики.

| Сценарий | Ожидаемый результат |
|---|---|
| Серия уточнений brainstorm с обновлением одного документа после ответов | Документ/память обновляются своевременно; каждый ответ не вызывает коммит. После самостоятельного проверенного результата — один коммит накопленных правок. |
| Несколько связанных исправлений одной проблемы, включая повторные проверки и правки отчёта | Один коммит после завершения и проверки общего результата; нет коммита каждой малой правки или каждого успешного теста. |
| Завершённые самостоятельные этапы длительной задачи | Проверенный документ требований, затем реализованная самостоятельная часть сохраняются отдельно; сообщения описывают результаты. |
| Явная команда пользователя сделать коммит сейчас в середине работы | Команда выполняется после соответствующих проверок разрешённых изменений; объяснено исключение и честно отмечена незавершённость. |
| Короткая задача: ideate → уточнения → документирование и проверка | Обычно один итоговый коммит целого результата; ни имя фазы, ни запись памяти не добавляют коммит. |
| Новый вопрос/задача при связанных незавершённых правках | Сам вход в задачу/набор не вызывает коммит и не включает чужой WIP. |
| План содержит множество commit-шагов; AS требует commit каждого increment | Частота подчиняется общему владельцу; связанные малые шаги группируются, workflow gates и проверки сохраняются. |
| Чистое дерево, уже сохранённый результат, посторонний index и exclude | Нет пустого/повторного коммита; чужие изменения и exclude остаются вне коммита. |
| Нужен снимок перед рискованной изоляцией/переносом/восстановлением | Объяснены операция и риск; проверенный промежуточный результат сохраняется как обоснованное исключение. Нет произвольного checkpoint по таймеру. |
| Ошибка проверки/коммита, отсутствующий Git или ce-commit | Нет ложного успеха и автоматического обхода; изменения сохранены, причина препятствия сообщена. |
| Коммит завершён | Сам по себе не вызывает push, PR, merge или переписывание истории. |

Повторить применимые сценарии для ideate, brainstorm, планирования, реализации,
проверки, исправлений и документирования, по отдельности для Codex и Claude,
