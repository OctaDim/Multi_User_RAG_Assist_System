# Обязательные границы создания и публикации

- Каждая новая заявка: отдельная `inbox/YYYY-MM-DD-суть-заявки/`. Контекст обязателен: когда возникла потребность, обстоятельства, причина, что решит выполнение, требуемый результат.
- Без явного указания пользователя создать в `harness/common/skills/` или `harness/project/skills/` сохранять в заявке контекст, результат и **полную папку скилла со всеми ресурсами**; по умолчанию не публиковать.
- `skill-creator` и внешние проверки обязательны во всех проектах. Нет инструмента — предупредить, предложить установку в окружение разработчика, статус «непроверен». Установка сама по себе не означает проверку.
- Для скиллов и правил перед переносом в harness и нативные каталоги проверять повторно; статусы Codex и Claude фиксировать отдельно. Полная проверка — успех у обоих для текущей версии. Недоступная/красная проверка требует явного разрешения на публикацию **непроверенной текущей версии**. Обычный запрос о переносе не является разрешением пропустить проверку; исключение не меняет статус на «проверен».
- При создании скилла/правила: сначала сохраняемый контракт и RED без новых инструкций, затем компактная версия и проверка итогового поведения. После правок повторить проверки; подробный порядок — `harness/common/docs/compact-authoring.md`. Уже компактный материал искусственно не ужимать.
- Применимые канонические comm-/proj- требования приоритетнее индивидуальных; skip/override запрещены. Конфликт common/project — согласовать и ждать ответа.

При создании или переносе скилла открыть lazy-процедуру из корня проекта: `harness/common/skills/comm-create-lazy-claude-codex-skills/SKILL.md`; контракт размещения — `harness/common/docs/skill-rule-ownership-contract.md`. Подробности на старте не читать.
