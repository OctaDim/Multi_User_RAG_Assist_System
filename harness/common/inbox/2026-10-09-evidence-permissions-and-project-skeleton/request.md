## Поручение пользователя

Пользователь поручил создать заявку на следующую матрицу прав:

| Операция | Evidence работы | Evidence harness |
| --- | --- | --- |
| Читать | Разрешено в рамках доступа к проекту | Разрешено |
| Создавать новые отчёты и результаты | В рамках порученной задачи, без дополнительного подтверждения каждого файла | В рамках согласованной обработки inbox |
| Дополнять отчёт текущей незавершённой работы | Разрешено; исходные результаты запусков сохраняются отдельно | Только в пределах разрешённой inbox-заявки |
| Исправлять завершённый отчёт | Новое датированное дополнение со ссылкой на прежний | Новое дополнение через inbox |
| Перезаписывать исходные логи и снимки | Запрещено; новый запуск — новый файл | Запрещено; новый запуск — новый файл |
| Удалять, переносить, переименовывать | Отдельное согласование состава и зависимых ссылок | Согласованный inbox с теми же проверками |

Основной принцип: **агент свободно записывает новые свидетельства порученной
работы, а изменения свидетельств самого harness проходят через inbox**.
Завершённые результаты сохраняют историю в обеих категориях.
Названия файлов продолжают отражать дату создания.

Дополнительное поручение пользователя: «Также нужно внести корректировку в
skeleton project harness для автоматического восстановления или создания».

## Обстоятельства и причина

В обсуждении предложено отделить evidence приложения и текущей работы от
evidence механизма harness и разграничить права изменения. Сейчас общий владелец
comm-protect-harness-evidence одинаково защищает common/testing/evidence и
project/testing/evidence; общий маршрут inbox требует заявку для любой записи
внутри harness. Одно создание новых папок это поведение не изменит.

Стартовая проверка ensure_entrypoint_links.py создаёт полностью отсутствующий
project из common/base/project-skeleton.json. В существующий project она сейчас
не добавляет недостающие категории и при отсутствии START.md/INDEX.md выдаёт
ошибку. Поэтому новую структуру нужно согласованно отразить в шаблоне и правилах
создания/восстановления. Удалённые рабочие материалы не восстанавливаются из шаблона.

## Разделение материалов

Предлагаемая в обсуждении структура текущего проекта:

```text
harness/project/testing/evidence/
  work/       — приложение, документы проекта и результаты текущих задач
  harness/    — механизм и подключение harness в конкретном проекте
```

Переносимые общие свидетельства механизма harness остаются в
harness/common/testing/evidence/. Проектно-зависимые материалы не переносить
в common только потому, что их предмет — harness.

Классифицировать по предмету проверки: результаты OCR, генерации и проверки
документации приложения — evidence работы; проверки правил, скиллов, стартовых
ссылок и механизма установки — evidence harness. Для смешанных материалов и
родительских операций не допускать обхода защищённого маршрута через work/.
Точные пути и карта существующих файлов фиксируются при обработке; переименование
или перемещение текущих evidence созданием этой заявки не разрешены.

3. Определить, когда рабочий отчёт считается завершённым, из текущего состояния

   Существующий project не заменяется пустым каркасом; данные приложения сохраняются.

6. Учесть связанные инструкции, установленное подключение и проверки, чтобы

   создание этой заявки не подтверждает их прохождение.

## Критерии будущей проверки

- Рабочий агент создаёт новый результат порученной задачи в work/ без новой
  inbox-заявки и без подтверждения каждого файла; текущий отчёт дополняется.
- Завершённый отчёт получает отдельное дополнение, а исходные логи и снимки
  сохраняются неизменными; новый запуск не перезаписывает прежний.
- Evidence механизма project требует project/inbox; evidence механизма common
  требует common/inbox. Рабочее поручение не даёт права править механизм.
- Удаление/перенос/переименование и операции над общими родителями сохраняют
  проверку состава, ссылок и отдельное согласование согласно матрице.
- Чистый common-only создаёт полный нейтральный project с обеими ветками evidence.
  После удаления всей project-папки повторный запуск создаёт тот же каркас без
  материалов предыдущего проекта и без заявления о восстановлении удалённых данных.
- Common+project сохраняет существующие файлы и результаты. Повторный запуск
  не переписывает заполненный каркас; проверяется побайтная сохранность.
- Частично отсутствующий каркас проверяется по отдельно принятой политике;
  её нельзя скрыто заменить полным пересозданием. Небезопасные пути/повреждённый
  шаблон дают отказ без порчи существующих данных. Project-only не поддерживается.
- Структурные проверки и нативное поведение агентов проверяются отдельно;
  непроведённые проверки и публикация не объявляются успешными.
