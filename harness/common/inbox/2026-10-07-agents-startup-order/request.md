# Исправить порядок старта с помощью AGENTS.md пользователя

Дата создания: 2026-10-07. Проект: GLOBAL_HARNESS_ENVIRONMENT. Пакет: common.

## Контекст и причина

Потребность возникла 2026-10-07 при проверке первого замечания аудита harness:
Codex открывал тело выбранного скилла до получения обязательных правил.
В исходном AGENTS.md порядок был выражен фразой о чтении INDEX.md и START.md
и списком ссылок; эта формулировка не обеспечивала требуемую последовательность.

Пользователь предложил файл с явным требованием «Прочитай в следующем порядке
(точный порядок очень важен)». Последний вариант задаёт одинаковый порядок
в обоих списках: common/START.md, project/START.md, .claude/rules,
common/INDEX.md, project/INDEX.md. Пользователь запросил создание заявки
для исправления с использованием этого файла.

материалом заявки, а не действующим входом текущего проекта.

## Требуемый результат

После согласованной обработки заменить корневой `AGENTS.md` полным кандидатом.
После обязательной стартовой команды Codex должен читать START.md обоих пакетов,
все машинные Markdown-правила .claude/rules с исключением README.human.md,
затем INDEX.md обоих пакетов. Все правила должны быть получены завершёнными
вызовами инструментов до начала чтения тела скилла.

Сохранить действующую стартовую команду и совместимость проверки ссылок.
Отдельный скилл или дополнительное постоянное правило для этого исправления
не требуется: ошибочное действие возникает на этапе статичного входа.
Существующий владелец диагностики входов — `comm-install-harness` и его
`references/entrypoints.md`.

При обработке проверить согласованность `BOOTSTRAP` и создания ссылок в
`harness/common/checks/ensure_entrypoint_links.py`: замена только корневого файла
сама по себе не меняет вход, создаваемый для новых установок. Необходимое
сопутствующее изменение генератора сначала представить отдельным конкретным
diff в этой заявке. Готового кандидата изменения генератора здесь пока нет.

## Проверки и сохранение результата при обработке

1. Сверить текущий корневой вход и кандидат, сохранить посторонние изменения
   пользователя и разрешить возможный конфликт до замены.
2. Проверить согласованный итоговый diff, стартовые ссылки, исключение человеческих
   пояснений и повторный запуск проверки входа без изменений.
3. Повторить применимые проверки текущей итоговой версии, включая порядок чтения
   при явном и неявном вызове в обоих режимах установки. Не повышать статус
   по одному лишь копированию ранее проверенного файла.
4. До закрытия перенести существенные результаты и исходные свидетельства
   в `harness/common/testing/evidence/` по действующим правилам размещения,
   чтобы они не зависели от существования временной заявки.
