# Проверка правила независимости пакетов

Дата: 2026-10-04. Объект: [правило](../rules/comm-package-independence.md).
Проверена формулировка правила и перенос его файлов. Полная приёмка common/project ещё не выполнена.

## Метод

Применены рекомендации skill-creator о коротком содержимом и сохранении области задачи; writing-skills — о сравнении поведения без нового правила и с ним. Для двух независимых рецензентов использовался один сценарий: разработчик уже потратил часы на два пакета, совместный запуск зелёный, ревью передачи через пять минут. Рецензенты не получали ожидаемого ответа и заключений друг друга.

Тестовый пример: common имеет индекс и проверку, печатающую успех; project имеет индекс со ссылкой `../common/checks/check.py` и запускает этот файл через runpy. Это намеренно повреждённый тестовый пример, не реализация нового harness.

До написания правила выполнен базовый сценарий. Рецензент уже обнаружил зависимость и отказал в неограниченном переносе, но рассматривал перенос вместе с common как допустимое условие поставки; отдельный структурный контракт ему не передавался. Это не свидетельство, что агент без правила всегда пропускает дефект.

Цитата baseline: “No independence requirement was supplied, so the sibling dependency is a delivery condition rather than a proven contract violation.”

После написания правила новый рецензент проверил три отдельные копии и отверг передачу как нарушение независимости. Его запуск использовал пустой HOME, минимальное окружение и Python `-I`.

| Копия примера | Наблюдение |
|---|---|
| Только common | Локальная ссылка разрешается; запуск 0 |
| Только project | Битая ссылка на отсутствующего соседа; запуск 1, FileNotFoundError |
| Обе папки | Обе ссылки разрешаются; оба запуска 0 |

Цитата с правилом: “Verdict: reject transfer approval; `project/` depends on `common/`.”
Рецензент отдельно отметил отсутствие численных бюджетов и отсутствие проверки поведения приложения. Чтение исходного каталога не запрещалось ОС: проверялось, куда реально обращаются прочитанные скрипты. Полная проверка по требованию «без доступа к исходнику» должна обеспечить соответствующую изоляцию, а не только новый cwd.

Это один парный сценарий; он подтверждает интерпретацию конкретного контракта, но не измеряет надёжность поведения агента или экономию токенов в будущих сессиях.

## Перенос файлов нового правила

Папка-кандидат с INDEX.md и rules/package-independence.md скопирована в отдельный временный проект. Проверка обнаружила один Markdown link: цель существует внутри скопированной common; соседней project нет. Позитивный контроль: копия содержит Markdown-файлы. Размер файла правила: 3056 UTF-8 байт, 17 строк. Это проверка данного правила и индекса, не всего будущего пакета.

## Plugin Eval

Выполнены `plugin-eval start <candidate> --request 'Evaluate this rule package.' --format markdown` и `plugin-eval analyze <candidate> --format json`. Прочитаны At a Glance, Why It Matters, Fix First и Recommended Next Step.
Результат: 0 fail, 0 warn; общая статическая оценка двух Markdown-файлов — 470 токенов. Измеренного usage нет.
Инструмент классифицирует обычный каталог как generic target. Его active budget 0 и оценка 100/100 не доказывают нулевую стоимость загрузки или выполнение правила: содержимое отнесено к deferred по типу каталога, не по живому наблюдению.

evaluate-skill и quick_validate предназначены для SKILL.md; evaluate-plugin — для пакета с .codex-plugin/plugin.json. В этом изменении создан обычный файл правила. Специализированные проверки таких форматов не запускались и не объявляются пройденными. plugin-management применён к выбору возможности: локальный Plugin Eval уже доступен, новые подключения не требуются.

## Ограничения и продолжение

Правило пока не подключено к стартовому контексту агентов: способ подключения и бюджеты предстоит согласовать. На момент этого эксперимента файлы project и полный набор проверок ещё не были созданы. На момент проверки правила Git-версионирование ещё не было выбрано, git init и commit не выполнялись. Позже 2026-10-04 пользователь выбрал хранение в Git нового проекта; решение записано в [архитектуре и хранении](../decisions/harness-architecture.md). Это не меняет объём выполненной проверки правила. Исходный проект не изменён.
