## User Flows

1. **Authorized application work → ordinary artifact.** Classify the content and operation, choose the existing project category, save directly, retain candidate/approved/planned/executed/actual-check status. This must also work when the user explicitly invokes the preservation or evidence skill; invocation changes neither the route nor task authorization. Covers R1, R4, R5 and AE1–AE4.
2. **Application task produces agent-governing knowledge.** A rule/procedure or executable harness check is mechanism work even when placed in docs or described as a test. Project mechanism follows project/inbox; common material follows common/inbox. An app task grants neither authority. Covers R2–R4, R6 and AE5–AE6.
3. **Evidence write or parent operation.** Pure app evidence within authorized ordinary work may be saved directly. Common evidence and project mechanism evidence retain their protected route. A mixed file or directory operation touching protected evidence follows that protection for the affected protected material; an app-only suboperation can be separated only when its scope is demonstrably independent. Covers R4, R8 and AE4/AE7.
4. **Unknown purpose or contradictory scope.** Inspect existing content and affected descendants before mutation. If purpose or authorization remains ambiguous, ask a focused question and pause the dependent action; do not classify by destination alone. Existing ownership rule already requires resolving conflicts before dependent work. Covers R4, R6, R8.
5. **Candidate instructions → validation → publication.** Prepared candidate and static copy equality do not establish native behavior. Unavailable native runs remain unverified per agent/mode; publication needs its separate exact-version gate. Existing content is not migrated or cleaned by this request. Covers R6–R7.

## Questions

No new user decision blocks implementation; the approved requirements and existing conflict/authorization rules supply the following defaults.

1. **A file combines app results and harness mechanism evidence: can app authorization rewrite it?** Stakes: protected evidence loss. Default: no; preserve the protected contract for the inseparable operation, without automatically migrating/splitting existing content.
2. **An operation targets a parent whose contents cannot yet be classified: should it proceed as app work?** Stakes: mechanism evidence could be affected indirectly. Default: inspect first, then pause dependent mutation if uncertainty remains; clarify only that uncertainty.
3. **A user explicitly invokes a preservation/evidence skill during an app task: does that require inbox?** Stakes: the everyday no-extra-request objective fails. Default: no; purpose and already authorized task scope govern. Explicit invocation grants no extra mechanism/common authority.
4. **Does ordinary app create/update permit bulk deletion or migration?** Stakes: unintended loss and expansion beyond R7. Default: no; direct persistence removes the extra inbox request for ordinary authorized saves/updates only and does not independently authorize cleanup or relocation.
