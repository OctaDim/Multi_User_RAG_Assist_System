## Поручение пользователя

Создать заявку в common harness, определяющую разделение:

- **`project/inbox`** — только изменения механизма проектного harness: его структуры, правил, процедур, проверок и управляющих настроек.
- **Соответствующие папки `project` напрямую** — обычная работа над приложением: идеи, исследования, принятые продуктовые и архитектурные решения, спецификации, планы, контекст продолжения и результаты проверок.
- **Изменения common harness** — отдельный маршрут через `common/inbox`; проектная работа его не затрагивает.

Такое разделение позволит защищать механизм harness, не создавая заявку при каждом сохранении рабочего материала. Сейчас эта граница в правилах не проведена: действующее объяснение описывает широкий порядок, при котором любые изменения внутри harness проходят через inbox.

## Обстоятельства и проблема

Пользователь уточнил, где находятся идеи и принятые решения RAG, и нужно ли
выполнять заявки project/inbox вручную. В обсуждении выяснено, что постоянные
результаты опубликованы в project/docs, project/decisions и project/handoffs,
но даже обычное сохранение этих материалов сейчас требует отдельной заявки.
Пример — продолжение ideate, оформленное отдельной заявкой project/inbox.
Пользователь считает такой порядок слишком медленным для повседневной работы.

Общий владелец маршрута сейчас требует inbox для всех создания, редактирования,
удаления, переименования и переноса внутри harness, включая отчёты и память.
Нужно изменить общий контракт, применимый к проектам, а не создавать исключение
для одной RAG-задачи. Работа над приложением не должна становиться разрешением
менять common harness.

## Требуемое разделение

1. Основание для project/inbox — изменение механизма project harness, а не само
   нахождение файла под harness/project. Защита охватывает структуру, управляющие
   правила и процедуры, исполняемые проверки механизма и управляющие настройки.
2. Идеи, исследования, принятые решения приложения, спецификации, планы,
   handoff и результаты проверок приложения сохраняются и обновляются сразу
   в соответствующих постоянных категориях project. Для обычного сохранения
   не создавать отдельную заявку project/inbox и не использовать inbox как
   хранилище рабочей памяти.
3. Изменения механизма common harness по-прежнему оформлять и обрабатывать
   через common/inbox. Поручение по приложению или механизму project не даёт
   разрешения изменять common.
4. Различать назначение материала: результат проверки приложения — рабочий
   материал, изменение программы проверки самого harness — изменение механизма.
   Архитектурное решение приложения — рабочий материал, изменение правил
   поведения агента — изменение механизма. Категория или имя файла сами по себе
   не определяют маршрут.
5. Не считать кандидаты идей принятыми решениями, согласованные требования —
   реализованными возможностями, а предполагаемые проверки — выполненными.
   Прямое сохранение рабочих материалов не меняет этих статусов.

## Критерии будущей проверки

- Сохранение идеи в project/docs, принятого решения приложения в project/decisions,
  плана в project/docs/plans и контекста в project/handoffs не создаёт inbox-заявку.
- Запись результата проверки приложения в project/testing/evidence не требует
  отдельной заявки только из-за места хранения результата.
- Изменение проектного правила, процедуры, проверки механизма, управляющей
  настройки или структуры project harness проходит через project/inbox.
- Изменение common harness проходит через common/inbox; обычная проектная
  работа не изменяет common.
- Проверяется смысл операции, а не только папка: одинаковое слово «проверка»
  не смешивает результат испытания приложения с изменением проверки harness.
- При будущем выполнении сохраняются применимые требования публикации и
  проверки инструкций; простое создание этой заявки не подтверждает их прохождение.
