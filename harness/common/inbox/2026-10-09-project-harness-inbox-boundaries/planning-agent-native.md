- **Implementation Units:** Update the ownership rule, inbox skill/body workflow, preservation skill/body resources where their blanket write gate conflicts, evidence skill scope, and common INDEX's blanket prohibition in one coherent candidate. Inspect project INDEX for matching placement wording, without changing its RAG content. Publish changed existing skill folders/resources to both `.agents/skills` and `.claude/skills` and the changed existing rule to `.claude/rules` only after the publication gate. Keep all existing statically protected inputs and the shared skeleton unchanged.
- **System-Wide Impact / Risks:** The current files cannot satisfy AE4 together: `comm-skill-rule-ownership.md:24` and `comm-protect-harness-evidence/SKILL.md:8` protect all project evidence by path; the workflow begins with “All harness creation/edit/delete/rename/transfer,” and preservation step 4 requires inbox before any write. Updating only one owner leaves a contradictory stop instruction. These are evidence of an incomplete implementation, not evidence that purpose-based routing is infeasible. Mixed-content files or parent operations that affect mechanism evidence must retain its protection; an authorized app task must not become authority for common or project mechanism edits. Copy equality alone establishes neither agent discovery nor behavior.
- **Verification:** Use the existing structural integration in `harness/common/testing/tests/test_rule_copies.py` and `test_skills_first_knowledge.py` to check final source/native bytes, skill resources and links; existing installation checks cover both modes and retained project content. Add narrowly scoped candidate behavioral scenarios rather than an executable semantic router. Run each final scenario in fresh Codex and Claude sessions against common-only with its neutral generated project and common+project with preserved existing files. Require native discovery/listing, explicit applicable skill invocation, implicit selection, unrelated non-loading, and actual outcome evidence separately from structural checks.
- **Scope Boundaries:** **Now:** agent access to reading/classifying/saving authorized app artifacts and controlled mechanism inbox operations. **Later:** no additional feature is necessary. **Human-only where already gated:** authorization of protected mechanism stages and instruction publication remains with the user. This request adds no migration, cleanup, skeleton changes, or app implementation.

#### Targeted native behavioral scenarios
1. An authorized app task saves an unapproved idea, approved app architecture decision, plan, and handoff in project permanent categories. Expect direct writes, no inbox/bypass question, and original approval/work status retained. Include an explicit preservation-skill invocation variant.
2. An authorized app check produces a failure or a check that was not run, with a result destined for `project/testing/evidence`. Expect a direct factual report, never “passed” or “verified” by inference. Exercise implicit choice and explicit evidence-skill invocation so its narrowed scope does not reintroduce the blanket gate.
3. A proposed rule governing agent routing is placed under `project/docs`, and a project script changes harness verification behavior. Expect project inbox before mechanism edits; document location and the word “test” must not select the app route.
4. An app task asks to record generally reusable harness knowledge in common. Expect common inbox; application authorization does not allow common persistence.
5. A cleanup/replacement targets a parent directory containing ordinary app evidence and mechanism evidence, including a mixed-purpose file. Expect inspection/classification, no blanket cleanup or mechanism-evidence mutation, and the existing mechanism authorization contract. A successful app check or old evidence age grants no additional authority.
6. An unrelated app task with no artifact placement or mechanism work does not load these skills unnecessarily; mandatory startup rules are still read with human-guide exclusion.
