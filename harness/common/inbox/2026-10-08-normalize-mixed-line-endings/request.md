# Сохранение политики нормализации смешанных LF/CRLF

Дата создания: 2026-10-08, Europe/Berlin.

## Контекст

- Потребность возникла 2026-10-08 в отдельной беседе о переносимости окончаний строк между Linux и Windows.
- Пользователь предложил при смешанных LF/CRLF приводить файл к LF и уточнил совместимость `.bat`/`.cmd` с LF. После обсуждения попросил: «сделай заявку для сохранения в харнес».
- Причина: единая нормализация всех типов файлов в LF может нарушить выполнение Windows batch-файлов; сохранение первого EOL при узком ремонте решает другую задачу.
- Проблема: действующий `comm-preserve-text-line-endings` требует сохранения байтов вне узкого ремонта и не содержит процедуры разрешённой полной нормализации по типу файла.
- Нужный результат: при отдельном запросе нормализации агент выбирает LF для обычного текста и CRLF для Windows batch-файлов, сохраняя содержимое и границы разрешения. Простой ремонт ссылки не запускает нормализацию всего файла.

## Разрешённая стадия

Разрешено создание этой заявки с полным кандидатом. Исполнение заявки,
проверка поведения кандидата, публикация, изменение существующих файлов
и нормализация реальных файлов требуют отдельного разрешения.
Прямой обход inbox не запрашивался. Заявки основной беседы не возобновляются.

## Предлагаемое решение

Подготовлен полный кандидат
[comm-normalize-text-line-endings](candidate-skills/comm-normalize-text-line-endings/SKILL.md).
Предлагаемый постоянный владелец —
`harness/common/skills/comm-normalize-text-line-endings/`.

Полная нормализация имеет отдельные входы (список файлов и разрешение),
результат (однородный EOL) и проверку (содержимое без изменения, идемпотентность).
Поэтому предложен отдельный компактный скилл без helpers и resources.
Действующий владелец узкого ремонта сохраняется. Постоянное стартовое правило,
новый роутер и автоматическая миграция файлов не предлагаются.

| Тип подтверждённого текстового файла | Целевой EOL |
|---|---|
| Markdown, Python, JS, JSON, YAML, обычный текст, `.sh` | LF |
| `.bat`, `.cmd`, включая расширения в другом регистре | CRLF |
| Формат с собственным требованием | Требование формата имеет приоритет |
| Неизвестный формат/кодировка, бинарный файл, отдельный CR | Не менять до выяснения |

Нормализация применяется ко всему явно указанному файлу только при разрешении
на эту операцию; наличие смешанных EOL само по себе не расширяет узкий ремонт.
Однородный файл нужного формата не перезаписывается. Уже однородный файл другого
формата конвертируется лишь при включении такой конверсии в разрешённую область.
Создание новых обычных текстовых файлов с LF — рекомендуемый default, а не
разрешение менять существующие файлы или добавлять обязательную стартовую загрузку.

Для AGENTS.md/CLAUDE.md остаются прежние ограничения: автоматическое
восстановление ссылок не разрешает полную нормализацию. Любая такая миграция
потребует отдельной согласованной обработки адресованной inbox-заявки.
Аналогично сохраняется маршрут защиты testing/evidence.

## Основания и ограничения

- [Git FAQ](https://git-scm.com/docs/gitfaq#_cross_platform_issues) рекомендует UTF-8 без BOM и LF для кроссплатформенного хранения текста; отдельно указывает LF для shell и CRLF для batch в рабочем дереве.
- [Microsoft: поддержка EOL в Notepad](https://devblogs.microsoft.com/commandline/extended-eol-in-notepad/) подтверждает чтение LF редактором Windows. Открытие в редакторе не доказывает корректное выполнение через cmd.exe.
- [CPython issue 61404](https://github.com/python/cpython/issues/61404) содержит историческое воспроизведение сбоя поиска batch-метки при LF и устранение после перехода на CRLF. Это не доказательство отказа каждого LF batch-файла на всех современных Windows.

Основания изучены в этой беседе; runtime-проверки на Windows не выполнялись.
Запрос EOL не включает смену кодировки, удаление BOM, форматирование содержимого
или изменение наличия конечного перевода строки.

## Границы исполнения

Предлагаемое исполнение — проверить и сохранить эту компетенцию в common,
без массовой нормализации репозитория. Полный опубликованный скилл и обычные
копии `.agents/skills`/`.claude/skills` должны совпадать.

После разрешения исполнения: выполнить обязательные проверки текущей версии,
сохранить основания и фактические свидетельства постоянно вне inbox через
согласованный маршрут, затем публиковать только после отдельного разрешения
публикации и применимого gate. Пока это только кандидат, а не действующая политика.

## Проверки при разрешённом исполнении

1. Frontmatter/имя/описание, компактность, plugin-eval через human-фильтр; результаты текущей версии без искусственного повышения статусов.
2. Временные UTF-8 fixtures с LF, CRLF и обоими порядками смешанных EOL; `.md`/`.sh` получают LF, `.bat`/`.cmd` и `.BAT`/`.CMD` — CRLF.
3. После нормализации сохраняются все байты содержимого кроме разрешённых разделителей строк, BOM и наличие/отсутствие конечного перевода строки. Повторный запуск не меняет байты.
4. Узкий ремонт без разрешения нормализации не меняет остальные EOL. Неизвестная кодировка/бинарные данные/отдельный CR и специальные требования формата не обходятся.
5. Сравнить LF/CRLF batch-fixtures с метками и вызовом подпрограммы на реальной доступной Windows через cmd.exe. Недоступность Windows означает «не проверено», а не гарантированную работоспособность.
6. Нативный выбор, явное применение, собственный контекст и незагрузка при постороннем запросе: Codex и Claude отдельно, common-only и combined. Проверка файлов не заменяет проверку поведения.
