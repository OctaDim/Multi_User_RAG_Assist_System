Стартовая проверка прошла. Применяю `comm-process-harness-inbox` для выбора формы опыта и `comm-create-lazy-claude-codex-skills` для критериев проверки. Сейчас уточню границу между скиллом и обязательным правилом, а также условия публикации при непроверенном Claude.

Выбор — **компактный lazy skill для диагностики CSV**: сценарий независимый, повторяемый, с точным trigger. В нативном каталоге подходящего CSV-скилла нет. Общая процедура относится к common; зависимая от конкретного проекта — к project.

Просьба коллеги сделать алгоритм обязательным не обосновывает always-loaded rule. По [experience-routing.md](harness/common/skills/comm-process-harness-inbox/references/experience-routing.md): «Обязательность алгоритма сама по себе не основание для always-loaded rule». Правило допустимо только при конкретном ошибочном действии **до выбора скилла**; тогда оно содержит короткую границу и указатель на процедуру.

Критерии проверки будущего кандидата:

- Точный trigger в `description`; в теле — применимость, обязательные действия, ограничения, остановки и наблюдаемый результат.
- RED без новой инструкции → компактный кандидат → GREEN; повторные проверки после правок.
- Отдельно Codex и Claude, оба режима: common-only и common+project; project-only должен отклоняться.
- Явный вызов, неявный выбор, чтение собственных ресурсов, отсутствие загрузки на посторонних задачах.
- Отдельные проверки исключения human README при чтении, в загрузчиках и поведении.
- Обязательные валидаторы; отчёт с версией, командами и статусами pass/fail/not-run с причинами.
