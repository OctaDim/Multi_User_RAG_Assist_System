В common checker уже используется чтение и запись байтов: исходный текст сохраняется, а окончания новых строк выбираются отдельно для каждого файла. `read_text()/write_text()` здесь не подходит: универсальная обработка переводов строк может изменить CRLF за пределами вставки. Срок и равенство смысла не расширяют разрешённый ремонт.

Проверю регрессии и сравнение с Git по коду. Тесты, создающие временные файлы, в этом read-only разборе запускать не буду.

Исправление уже есть в [common checker](harness/common/checks/ensure_entrypoint_links.py). Предложение коллеги использовать `read_text()/write_text()` отклоняется: одинаковый смысл не гарантирует сохранение байтов CRLF.

Правильное поведение:

- Читать `read_bytes().decode('utf-8')`, записывать `write_bytes(text.encode('utf-8'))`; ошибки UTF-8 останавливают ремонт.
- Сохранять исходные байты, включая смешанные окончания строк.
- Для вставок брать первый LF/CRLF **каждого файла отдельно**, при отсутствии — LF.
- В `AGENTS.md` добавлять только отсутствующие стартовые ссылки и указание чтения правил. В `CLAUDE.md` добавлять отсутствующий `@AGENTS.md`, сохраняя прежнее содержимое.
- Распознавать корректный CRLF-импорт без повторной вставки.
- Перед восстановлением выводить уведомление. Повторный запуск должен сохранять байты без дублей и сообщения о повреждении.

Проверки должны выполняться на временных fixtures: LF/CRLF, сохранение исходного префикса, байты вставок, отдельный CRLF у CLAUDE, повторный запуск. В Git-fixture — сравнение с `HEAD` без ложного предупреждения после восстановления CRLF-ссылок; одного `git diff` недостаточно для доказательства сохранности байтов.
