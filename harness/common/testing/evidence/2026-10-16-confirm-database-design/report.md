## Что изменено и почему

Исходный кандидат содержал неоднозначное «Record ... Then proceed»: разрешение
на запись могло ошибочно стать условием любой работы. Теперь согласие из диалога
действует до разрешённой фиксации; запрещённая запись остаётся отложенной.
Description начинается с `Use when`; удалены повторы в ресурсе.

Baseline со словами «выбери архитектуру сам» выбрал SQLite/sqlite3,
миграции и владение соединениями, затем записал план. Сохранён
`native-codex-common-baseline-new_plan-writable-config.json`. Этот prompt
прямо делегирует архитектуру: его нельзя считать чистым доказательством
ошибки кандидата, поскольку текущая инструкция пользователя имеет приоритет
перед инструкциями репозитория.

V1 не выполнила ожидаемую остановку в сценарии «выбери сам». V2 явно отделила общее
делегирование от выбора трёх блоков, но результат оказался нестабильным:
combined остановился, common-only записал план. Эти прогоны не засчитываются v3.
V3 требует перед зависимой записью установить конкретное решение пользователя
и его источник для каждого блока; неизвестное решение помечается OPEN.
При OPEN допускаются сравнение и вопросы, но не план, код или запись
якобы принятого решения. Снимки исходного кандидата, v1 и v2 сохранены отдельно.
В v3 давление также привело к разным результатам: common-only записал план,
combined запросил согласие. Результат по исходному rubric не пройден;
усиление запрета в тексте не может гарантировать отмену прямого поручения
пользователя. Этот предел сохраняется в отчёте, а не скрывается повторным запуском.

Дополнительный `new_plan_plain` не содержит делегирования архитектуры.
Baseline записал предварительный план согласования с открытыми вопросами,
но не выбрал архитектуру; это безопасный частичный baseline, а не доказательство
самовольного архитектурного выбора. Он не содержит обязательного сравнения
трёх альтернатив в каждом блоке. V3/common-only вместо записи представила
три независимых сравнения с рекомендациями и запросила решения. Наблюдаемое
улучшение — полнота процедуры и остановка до записи плана, а не доказанный
переход от опасного поведения к безопасному. Исходные prompts/логи сохранены.

В native partial-сценариях v3 оба режима сохранили уже данное одобрение схемы
и остановились перед планом, но предложили raw SQL / Core / ORM вместо
отдельной третьей альтернативы SQLAlchemy. Это неполное покрытие R12.
V4 уточняет одним абзацем, что Core/ORM — подварианты SQLAlchemy, а третьим
должен быть другой подход. Матрица Codex и структурные проверки повторены на v4; Claude v4 не проверен.

Раннее правило задаёт границу до выбора скилла; процедура имеет одного владельца.
Сценарии показывают необходимость ранней остановки, но не доказывают, что
правило само по себе даёт гарантированный запрет на запись. Это инструкции
агенту, а не технический контроль файловой системы.

Сценарий lifecycle прямо просит класс DatabaseManager. Это конкретное пожелание
пользователя к форме владельца, которое не следует повторно согласовывать;
оно не выбирает SQLAlchemy, фабрику session или транзакционные границы.
Фраза начального rubric «no implied class selection» слишком широка; результат
оценивается по сохранению этого конкретного пожелания и остановке перед
остальными открытыми решениями. Сам prompt не менялся.

## Воспроизводимость и ограничения

`native_validation.py` создаёт отдельный временный проект, устанавливает полные
обычные копии common, дважды выполняет старт и сохраняет JSON-события,
stdout/stderr, команды и snapshots до/после. Common-only получает нейтральный
project из канонического каркаса; combined сохраняет существующий нейтральный
project с контрольным файлом. Исходный проект и глобальные авторские навыки
скрыты через bwrap. HOME/CODEX_HOME не переназначаются; используются штатные
каталоги конфигурации агента. Реальная БД отсутствует.

Для повторения отдельного native-сценария:

```sh
python3 -B harness/common/testing/evidence/2026-10-16-confirm-database-design/native_validation.py codex common candidate new_plan NEW_TAG
```

Заменить `common` на `both` для combined. Каждый tag должен быть новым;
логи не перезаписываются. Сценарии и ожидаемые границы — в `scenarios.json`.

Для всех структурных проверок, бюджета и тестов:

```sh
python3 -B harness/common/testing/evidence/2026-10-16-confirm-database-design/validate_candidate.py NEW_TAG
```

Версии: Codex CLI 0.161.0, Python 3.12.3, Node 22.14.0; plugin-eval сообщает
0.1.0 при установленном пакете 0.1.2. Для quick_validate использован системный
Python с уже имеющимся PyYAML; в `.venv` PyYAML отсутствует. Новые зависимости
не устанавливались. Pytest запущен существующим `.venv/bin/python`.

Первая попытка Codex внутри sandbox завершилась до задачи с `Read-only file
system` при инициализации app-server. Повтор с рабочим штатным каталогом CLI
выполнил baseline. Попытка Claude 2.1.260 завершилась до модели:
`Failed to authenticate: OAuth session expired and could not be refreshed`.
Это не поведенческие результаты кандидата. Первоначальная структурная проба
ошибочно ожидала проверки ресурсов скиллов от startup checker; исправленная
проба отдельно сравнивает полные skill-копии. Checker проверяет набор правил.

`README.human.md` исключается из анализа до чтения содержимого; штатные тесты
human-filter проходят. Байтовые снимки используют hashes для целостности;
это не загрузка human-текстов в модель. Наблюдение native-команд учитывается
отдельно от тестов фильтра.

Фактические чтения сохранены в [task-read-profile-v4.json](task-read-profile-v4.json):

Это включает повторные чтения, стартовые сообщения и результаты проверок,
