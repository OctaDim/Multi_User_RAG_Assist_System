# Сохранение визуального решения: результат проверки lazy-only v2

Дата создания: 2026-10-19, Europe/Minsk.
Состояние: подготовка и проверка кандидата завершены; публикация ожидает решения.

Подготовлен один lazy-скилл `comm-preserve-visual-design`, без нового постоянного
правила. Тело — 176 слов. Все Scope 1–7 исходной заявки сохранены: конкретный
референс и версия, границы визуальных согласований, делегирование, существенные
отклонения, фактическая сверка рендеров, отдельные результаты поведения/структуры/
оформления и честный статус завершения.

## Основание и выбор формы

Заявка: `harness/common/inbox/2026-10-19-preserve-approved-visual-design/request.md`.
План: `harness/common/docs/plans/2026-10-19-1307-preserve-approved-visual-design-plan.md`.
В этой сессии выбран маршрут using-superpowers + ce-brainstorm → ce-plan → ce-work.
Прямое уточнение пользователя задаёт переход от rule+skill к lazy-only и исполнение.

Сравнение трёх форм:

| Форма | Вывод |
| --- | --- |
| Только правило | Недостаточно: есть самостоятельная контекстная процедура; её постоянная загрузка в несвязанных задачах избыточна. |
| Только lazy-скилл | Достаточно: UI-реализация, утверждённый референс и визуальная приёмка распознаются по метаданным; алгоритм остаётся у одного владельца. |
| Правило + скилл | Не обосновано: конкретной предшествующей ошибки, которую нельзя предотвратить discovery скилла, не установлено. |

Отдельного владельца этого результата в действующем common не найдено. Новый
владелец отвечает за сохранение конкретного визуального контракта; действующие
процедуры размещения и evidence остаются владельцами своих операций. Пропуск
подключения не разрешает автоматически создавать rule-trigger.

Исходный кандидат правила исключён из актуального состава. Исходные машинные
тексты и хеши сохранены в `original-inputs.json`; прежний SKILL в inbox —
историческая v1. Текущий полный кандидат —
`candidate/comm-preserve-visual-design/` внутри заявки. Его неизменный полный
снимок вне inbox — `candidate-v2/comm-preserve-visual-design/` в этой папке.

## Контроль, найденный пробел и уточнение

Выполнены пять свежих контрольных сессий без новой инструкции и два нативных
контроля в изолированных установках. Уже без скилла Codex правильно сохранял
A-v3, отвергал самовольную замену компоновки, отличал queued от approval и не
переспрашивал разрешённые исправления. Общего улучшения этих решений не доказано.

Наблюдаемый узкий пробел: в предложении нового оформления (сценарий 2) контроль
и исходная v1 не включали адаптивность в предмет визуального согласования;
правильная проверка уже утверждённых 1280/390 из сценария 10 этого не заменяет.
В четырёх профильных native-ответах v1 адаптивность в этом согласовании отсутствует;
в четырёх соответствующих native-ответах v2 и пяти свежих micro-ответах v2 она
названа явно. Это наблюдение по реальным ответам и документам, не тест слов.

Независимое ревью также обнаружило текстовую неполноту: исходный скилл требовал
записать свойства, но не требовал явно сохранить местоположение и версию
референса в постоянном проектном материале. Неуспех выбора актуальной версии
в контроле не воспроизведён; текстовый пробел не выдаётся за поведенческий провал.
В v2 это требование записано явно. Оба уточнения закрыты; независимое ревью
текста v2 и наблюдаемых результатов завершено без оставшихся замечаний.

## Реальные изображения и пределы доказательства

В одноразовых проектах Chromium 131.0.6778.33 отрендерил утверждённую левую
навигацию и текущую верхнюю при 1280×800 и 390×800. Скрипт проверил функциональный
Send → Done по фактическому DOM. Нативный агент не нажимал кнопку повторно и
корректно обозначил функциональный результат как предоставленное свидетельство.

В первых двух render-прогонах выводы были правильными, однако CLI JSON не
содержал событий view_image. Утверждение отчёта о просмотре не считалось
доказательством фактического предоставления PNG. Старые логи сохранены без правок.
В новых `v2-native-render-attached-common.json` и `...-both.json` все четыре PNG
переданы напрямую отдельными `-i` с подтверждёнными именами и SHA-256. Эти
проверки подтвердили: левая навигация заменена верхней на desktop; mobile PNG
совпадают; тест кнопки не компенсирует структурное/визуальное несоответствие.

Это проверка поведения инструкции на синтетическом UI. Она не подтверждает
соответствие или готовность реального приложения RAG, работу непоказанных
состояний, повторные пользовательские клики или обычный запуск приложения.

## Инструменты и воспроизводимость

Codex CLI 0.161.0, Node 22.14.0, Python 3.12.3, PyYAML 6.0.1,
pytest 8.4.2, plugin-eval из пакета 0.1.2 (report tool version 0.1.0),
Chromium 131.0.6778.33. Модель CLI отдельным флагом не закреплялась;
результат не обобщается на любые модели/версии.

Использованы bwrap, отдельный временный CODEX_HOME без пользовательского конфига,
маскирование исходного проекта, глобальных навыков и плагинов, полные локальные
native-каталоги. В проверочных заданиях явно выбран самостоятельный маршрут;
полное поведение внешней CE-цепочки этими сценариями не оценивается.
Зависимости не устанавливались. Первичная проверка доступности показала отсутствие
PyYAML в .venv; quick_validate выполнен системным Python с установленным PyYAML.

Полные исходники используемых методов и их хеши сохранены в
`validation-methods-source.json`; историческая база определяется
`original-inputs.json`, а не будущим состоянием canonical-пути. Для повтора
нужны новые имена raw-логов; старые результаты не перезаписывать. Скрытые
чтения загрузчика на уровне ОС отдельно не инструментировались.
