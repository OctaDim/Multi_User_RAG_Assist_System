## Полное содержание изменения

В начале сообщения пользователь дополнил прежнее описание: общий для сервиса
лимит из отдельного конфигурационного файла может изменяться супер-админом через
админку; изменения сразу начинают действовать. Далее пользователь явно заменил
прежнюю модель «3 активные генерации, остальные в очереди» следующей спецификацией:

1. По умолчанию допускается до 12 активных запросов. Каждый запрос имеет отдельный
   контекст и состояние формируемого ответа; данные разных пользователей не смешиваются.
2. За один шаг генерации продвигаются до 3 активных запросов: для каждого вычисляется
   следующий токен. Затем обслуживается следующая группа. Вычисления распределяются
   справедливо между активными запросами, чтобы они получали текст постепенно,
   не ожидая завершения всего ответа другого пользователя.
3. Запросы сверх лимита 12 ожидают в очереди.
4. Дефолтные значения 12 и 3 задаются в конфигурации и применяются при запуске
   сервиса. Уполномоченный администратор может менять оба ограничения через админку
   без перезапуска.

Значение 3 теперь означает число запросов, продвигаемых за шаг, а не число
одновременно активных ответов. Оба ограничения общие для сервиса и не умножаются
числом API-процессов. Право изменения записывается за super_admin, прямо названным
в начале поручения; новый доступ для обычного admin этим изменением не утверждается.

Это согласованное требование, а не уже реализованная или проверенная возможность.
При техническом проектировании проверить поддержку выбранным runtime, память
для 12 контекстов и скорость выдачи. Отдельно определить поведение при уменьшении
лимитов во время работы и сохранение изменений админки после перезапуска.
В рамках этого поручения обновляется документация; приложение не реализуется.
