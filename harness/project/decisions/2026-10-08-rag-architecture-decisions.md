Решение RAG-42 добавлено: 2026-10-13, общая история и один выполняющийся запрос при нескольких вкладках беседы.

Решение RAG-48 добавлено: 2026-10-13, удаление черновиков при закрытии их вкладки.

Источник: прежний Multi-Users_RAG_Assistants, read-only. Рабочая папка:

реализация приложения этим переносом не начинается.

Этот реестр собирает 49 согласованных решений: 32 перенесены из прежнего проекта,
RAG-33–RAG-49 приняты при продолжении обсуждения в текущем проекте. При импорте тексты
сохранены без сокращения; RAG-11/RAG-12/RAG-13/RAG-14/RAG-21/RAG-30/RAG-31 обновлены 2026-10-09.

запись о согласовании в документах: исходные реплики пользователя сохранились
не для всех решений. Нельзя повышать это до подтверждения полной стенограммой.

## Реестр решений

| ID | Решение | Основание и последствия | Критерий будущей реализации |
| --- | --- | --- | --- |
| RAG-01 | Один прикладной backend | Общие операции для пользовательского веб-интерфейса, будущих клиентов и административных действий. | Один общий набор серверных операций для всех клиентов. |
| RAG-02 | Гибридный монолит | Один проект с папками `backend/` и `frontend/`. У частей независимые зависимости, конфигурация, запуск и развёртывание; каждая может размещаться на отдельной машине. | Backend/frontend независимо запускаются и размещаются; связаны HTTP API. |
| RAG-03 | API на async FastAPI | Выбор пользователя. Асинхронный ввод-вывод для запросов к БД и AI-провайдерам; тяжёлая обработка файлов вынесена из процесса API. | HTTP API асинхронный; тяжёлая обработка не блокирует event loop. |
| RAG-04 | Фоновая обработка документов | Парсинг, нарезка, создание эмбеддингов и индексация выполняются отдельно от HTTP-запроса загрузки. | Загрузка получает статус; обработка выполняется вне HTTP-запроса. |
| RAG-05 | Файловое хранилище | Оригиналы документов сохраняются отдельно от поискового индекса. Конкретное размещение хранилища ещё не выбрано. | Оригинал доступен отдельно от векторов; размещение ещё проектируется. |
| RAG-06 | PostgreSQL с pgvector | Основная БД для прикладных данных и векторов. Отдельная векторная БД на старте не требуется выбранной архитектурой. | Прикладные данные и векторы сохраняются в PostgreSQL/pgvector. |
| RAG-07 | Аккаунты и внутренняя админка сразу | Вход, идентификация пользователя и административный интерфейс входят в первый релиз. Админка через API выбрана; конкретная библиотека аккаунтов ещё не утверждена. | Аккаунты и админка присутствуют в первом релизе. |
| RAG-08 | Вход по email/паролю | Выбор пользователя. OIDC/SSO не входят в выбранный начальный сценарий. Конкретная библиотека аккаунтов ещё не утверждена. | Вход email/пароль; SSO не становится обязательной зависимостью. |
| RAG-09 | Самостоятельная регистрация с подтверждением email | Подтверждено пользователем 2026-10-03. Email подтверждается при регистрации до доступа к загрузке и RAG; подтверждение не снимает административную блокировку. | Без подтверждённого email загрузка и RAG недоступны. |
| RAG-10 | Масштаб MVP | 30 пользователей, до 10 одновременно. Это целевая нагрузка, а не результат нагрузочного теста. | Совместное испытание 10 пользователей при 30 аккаунтах ещё требуется. |
| RAG-11 | Активные запросы, справедливые шаги генерации и очередь | Согласовано пользователем 2026-10-09: по умолчанию до 12 активных запросов с отдельными контекстами и состояниями ответов; за шаг до 3 запросов получают следующий токен каждый, затем обслуживается следующая группа. Продвижение справедливое, данные пользователей не смешиваются; запросы сверх 12 ждут в очереди. Оба лимита задаются отдельным конфигурационным файлом при запуске, общие для всего сервиса и меняются super_admin через админку с немедленным действием без перезапуска. | Проверить 12 активных запросов и очередь сверх лимита, изоляцию контекстов/ответов, до 3 запросов за шаг, справедливую постепенную выдачу и изменение обоих лимитов без перезапуска; API-процессы не умножают ограничения. Возможность ещё не реализована и не проверена. |
| RAG-12 | Форматы, OCR печатного текста и рукописей, персональные разрешения | PDF, DOCX, TXT, Markdown и OCR входят в MVP. С 2026-10-09 OCR печатного и рукописного текста в PDF включён для русского, белорусского, английского и немецкого языков; обработка выполняется фоновым worker. Для каждого пользователя нужны отдельные поля разрешений загрузки PDF, DOCX, TXT, Markdown и OCR рукописей для будущей раздельной тарификации. Отдельная загрузка фотографий не включена. | Проверить каждый формат и OCR печатного/рукописного текста каждого языка на реальных файлах; backend соблюдает персональные разрешения и не позволяет обходить их прямым API-запросом. Возможность ещё не реализована и не проверена. |
| RAG-13 | Дефолтные и персональные лимиты документов | Дефолты: 50 МБ на файл, 500 страниц на PDF, до 20 файлов в одной загрузке, до 1000 документов и 2 ГБ оригиналов на пользователя. Все пять значений настраиваются в конфигурации; с 2026-10-09 также задаются для каждого пользователя отдельно для будущей раздельной тарификации. | Проверить разные индивидуальные значения всех пяти лимитов для двух пользователей, пограничные значения и параллельные загрузки; изменение одного пользователя не меняет ограничения другого. Это согласованное требование, не результат испытаний. |
| RAG-14 | Три роли и границы административных настроек | `user`, `admin`, `super_admin`. Обычный администратор не читает чужие документы и переписки; super-admin имеет явное право их чтения через защищённый административный API. С 2026-10-09 только super_admin меняет глобальные динамические настройки и лимиты через админку; admin не может менять глобальные значения, но может менять лимиты отдельных пользователей. | Проверить права всех 3 ролей: super_admin меняет глобальные настройки/лимиты, admin получает отказ для глобальных изменений и может менять персональные лимиты; чтение чужих данных admin запрещено. Права проверяет backend, включая прямые API-запросы. |
| RAG-15 | Только личные библиотеки в MVP | Без организаций, команд, общих папок и предоставления документов другим пользователям. Подтверждено пользователем; административное право чтения super-admin сохраняется и не означает совместный RAG. | Пользовательский поиск не включает чужие библиотеки. |
| RAG-16 | История после удаления документа | Прежние ответы сохраняются с отметкой «источник удалён» и исключаются из дальнейшего контекста модели. Удалённый материал также исключается из поиска, checkpoint-состояния и резюме, используемых для новых ответов. | Удалённый источник не возвращается через поиск, историю контекста или resume. |
| RAG-17 | Только мягкое удаление аккаунта в MVP | `active=False` означает мягкое удаление с сохранением документов и переписки. Физическое удаление аккаунта и всех его данных в MVP не входит. | Мягкое удаление сохраняет документы, сообщения и checkpoints. |
| RAG-18 | Будущая активация доступа оплатой | Направление подтверждено пользователем; провайдер, тарифы и реализация биллинга пока не выбраны. Сам биллинг не входит в текущую реализацию. | Биллинг не реализуется в MVP; его параметры не выбраны. |
| RAG-19 | Весь веб-интерфейс работает через API | Пользовательский кабинет и админка находятся во frontend и вызывают API backend. У браузера нет прямого доступа к БД, хранилищу или секретам AI-провайдера. | Браузер использует API; секретов backend в frontend нет. |
| RAG-20 | Админка через API | Выбор пользователя. Административные маршруты FastAPI проверяют права, вызывают общие операции и фиксируют изменения. Готовая ORM-панель не выбрана. | Административные операции проходят серверную авторизацию и аудит. |
| RAG-21 | Приоритет состояний доступа | Сначала `active`, затем `disabled`, затем `paid`. `active=False` — мягкое удаление; по уточнению пользователя 2026-10-09 `disabled=True` — административная блокировка, `disabled=False` — отсутствие такой блокировки; `paid=False` — не оплачен, `paid=True` — оплачен. Для MVP `paid` не проверяется. | MVP: active=True AND disabled=False; paid не влияет на доступ. После включения биллинга дополнительно требуется paid=True. Аутентификация, подтверждение email, роль и владение ресурсом проверяются отдельно. |
| RAG-22 | Область поиска | По умолчанию все готовые личные документы; при создании беседы можно выбрать конкретный набор. Удаление выбранных документов не расширяет поиск на остальные без выбора пользователя. | Удаление выбранных документов не расширяет область поиска. |
| RAG-23 | Ограничения при прекращении доступа | Запрет новых защищённых операций, прекращение дальнейшей выдачи ответа, остановка фоновой обработки на безопасной границе. Документы и история сохраняются. Правила действуют для мягкого удаления, административного отключения и в будущем отсутствия оплаченного доступа. | Блокировка прекращает новые операции/поток; worker останавливается безопасно. |
| RAG-24 | Резервные копии | Согласованная копия БД и оригиналов ежедневно, срок хранения каждой копии 7 дней. Для MVP пользователь выбрал папку `_RESERVED_COPIES/` в корне проекта на том же диске; папка и всё содержимое исключены через `.gitignore`. Это не защищает от отказа диска. При восстановлении учитываются последующие удаления и изменения доступа. | Ежедневная согласованная копия, ротация 7 дней, восстановление с последующими ограничениями. |
| RAG-25 | Беседы сохраняются на сервере | История сообщений принадлежит аккаунту и не зависит от открытой вкладки браузера. | История доступна после закрытия вкладки. |
| RAG-26 | Потоковый ответ и остановка | Подтверждено пользователем: текст появляется постепенно по мере генерации, в UI есть кнопка остановки. Поток передаётся через HTTP API (SSE); остановка выполняется серверной операцией с проверкой владельца беседы. | Остановка отменяет генерацию на сервере и освобождает слот. |
| RAG-27 | Приёмка качества RAG | Все 30 из 30 заранее подготовленных контрольных вопросов по реальным документам должны дать корректный результат. Допустимого числа ошибок нет. Все проверки прав, удаления и очереди также должны пройти. Это требование к будущей приёмке, а не уже достигнутое качество. | 30/30 заранее зафиксированных вопросов; все проверки доступа, удаления и очереди. |
| RAG-28 | Локальный агент LangGraph внутри backend | Async FastAPI вызывает граф асинхронно. Граф учитывает контекст, выполняет разрешённый RAG-поиск, вызывает LLM и сохраняет состояние. | Граф вызывается асинхронно из backend. |
| RAG-29 | Состояние LangGraph в PostgreSQL | Используется `AsyncPostgresSaver`; `thread_id` идентифицирует беседу, но не даёт права доступа. Backend проверяет владельца до любого обращения к её состоянию. | Владелец проверяется до чтения/запуска/возобновления checkpoint. |
| RAG-30 | Модели локального MVP и доступность настроек в админке | `multilingual-e5-small` ONNX INT8 через ONNX Runtime CPU для эмбеддингов; `Qwen3.5-2B` GGUF Q4_K_M через llama.cpp CPU для генерации. Выбор подтверждён пользователем 2026-10-03 после локальных проб. Базовые настройки: `-t 4 -tb 8`, контекст запроса 4096, thinking выключен. С 2026-10-09 действующее требование RAG-11 — 12 активных запросов и до 3 продвигаемых за шаг; прежние измерения выполнены с одним слотом. Параметры моделей отображаются в админке super_admin: требующие перезапуска процессов disabled для изменения, изменяемые без перезапуска enabled. | Пара моделей и базовые параметры сохранены; проверить отображение обеих категорий и серверный запрет изменения параметров, требующих перезапуска, включая прямой API. Фактическую поддержку изменений без перезапуска выбранным runtime и интеграцией ещё проверить. Требование не реализовано и не проверено; поддержка новой модели RAG-11, память для 12 контекстов и скорость выдачи также ещё не проверены. |
| RAG-31 | Бесплатный внешний fallback с возвратом на локальную LLM | Если локальная LLM слишком медленная или не проходит проверку качества, эмбеддинги остаются локальными, генерация может использовать только проверенный бесплатный API. Платное переключение запрещено. С 2026-10-09 во время внешней генерации сервис периодически проверяет локальную LLM; при одновременном прохождении проверок скорости и качества автоматически возвращает генерацию на локальную модель. Граница для начатых и ожидающих ответов согласована 2026-10-10 в RAG-39. | Внешний маршрут включается отдельно после проверки бесплатности и согласия на передачу данных. Проверить периодические локальные пробы, отсутствие возврата при провале хотя бы одного критерия, возврат при выполнении обоих и границу RAG-39; это согласованное требование, не реализованная или проверенная возможность. |
| RAG-32 | Проверка GLM отложена до необходимости fallback | По указанию пользователя проверка нативной `glm-4.7-flash` остановлена 2026-10-03. Если понадобится внешний fallback, сравнить режимы с thinking и без него, русский RAG, задержки и ограничения API. В локальном MVP этот маршрут не включается. | API-пробы GLM не возобновляются без нового поручения при необходимости fallback. |
| RAG-33 | Ранний показ найденных фрагментов входит в MVP | Согласовано пользователем 2026-10-10: найденные фрагменты разрешённой личной библиотеки показываются до готовности генерации, в том числе во время ожидания в очереди. Генерация продолжается автоматически; пользователь может отменить свой запрос, если фрагментов достаточно. | Проверить показ доступных фрагментов до первого токена, соблюдение выбранной области поиска и прав доступа, отмену запроса и сохранение ограничений RAG-11. Требование ещё не реализовано и не проверено. |
| RAG-34 | Паспорт оснований и границ ответа входит в MVP | Согласовано пользователем 2026-10-10: компактный блок с раскрываемыми подробностями показывает фактическую область поиска, использованные источники и фрагменты, различает цитаты и выводы и сообщает о неготовых или исключённых документах выбранного набора. Отсутствие найденных оснований не означает отсутствия факта во всей библиотеке; область поиска не расширяется автоматически. | Проверить соответствие паспорта фактическому поиску и использованным источникам, различение цитат и выводов, отображение ограничений выбранного набора и соблюдение прав доступа. Требование ещё не реализовано и не проверено. |
| RAG-35 | Сверка и исправление рукописного OCR входят в MVP | Согласовано пользователем 2026-10-10: распознанный текст связан с исходной страницей, проблемные места извлечения видны владельцу; он может добровольно сверять и исправлять текст. возможность. Состав оценок, представление неизвестных последствий и точность

это обозначается, а не выдаётся за успешную проверку. Предварительная оценка
не резервирует квоту и не гарантирует допуск: backend повторно проверяет
ограничения при загрузке с учётом параллельных операций и действующих персональных
значений. Персональные разрешения форматов и OCR из RAG-12 и проверки доступа
сохраняются; помощь в подборе пачки не позволяет их обойти.

**Статус:** согласованное требование MVP, не реализованная и не проверенная
возможность. При проектировании определить место и стоимость проверки страниц
PDF, представление неизвестных данных и способ предложения вариантов уменьшения
пачки. Дополнительное резервирование квоты этим решением не вводится.
Идеи №6/№7 этим решением не согласованы.

## Решение RAG-38: поиск опровергающих фрагментов, 2026-10-10

Основание — ответ пользователя «Включить в MVP» на вопрос о поиске фрагментов
за и против утверждения по явному запросу, внутри выбранных личных документов,
с оговоркой: отсутствие найденного опровержения не считается доказательством
истинности. Принята идея №6 из
[обзора идей](../docs/ideation/2026-10-09-personal-rag-ideation.html#g19).

Владелец может отдельным запросом попросить проверить, есть ли в выбранных
документах основания против утверждения. Сервис ищет доступные фрагменты
за и против внутри того же выбранного набора, показывает источники и учитывает
различия даты, объекта и условий: разные обстоятельства могут объяснить
расхождение без настоящего противоречия. При отсутствии найденного опровержения
сообщается об ограниченности поиска, а утверждение не объявляется доказанным.
Действуют RAG-15/RAG-16/RAG-22 и проверки доступа; поиск не расширяется
автоматически за пределы выбранных документов.

Это явный новый запрос пользователя; автоматическая перепроверка старых ответов
остаётся отложенной. Дополнительный поиск и генерация подчиняются действующим
ограничениям сервиса RAG-11.

**Статус:** согласованное требование MVP, не реализованная и не проверенная
возможность. При проектировании определить представление сопоставляемых
фрагментов и проверить качество различения противоречий и разных обстоятельств
на реальных документах. Качество поиска и дополнительная нагрузка не проверены.
Идея №7 этим решением не согласована.

## Решение RAG-39: граница возврата к локальной модели, 2026-10-10

Основание — ответ пользователя «Согласуем эту границу переключения» на предложение
сохранить модель для уже начатого ответа и выбирать актуальную модель для новых
и ожидающих запросов при допуске к генерации. Принята идея №7 из
[обзора идей](../docs/ideation/2026-10-09-personal-rag-ideation.html#g02).
Уточняется уже согласованный автоматический возврат RAG-31 после успешных
проверок скорости и качества одновременно.

Начатый ответ сохраняет модель, на которой началась его генерация; при обычном
возврате на локальную модель генератор посреди этого ответа не меняется.
Новые запросы после возврата обслуживает локальная модель. Для запросов,
ожидающих в очереди, маршрут выбирается при допуске к генерации, поэтому они
также используют актуальный маршрут, а не закреплённый в момент постановки
в очередь. При допуске повторно проверяются доступ и условия передачи данных.
Ограничения допуска и продвижения RAG-11 и отдельные состояния пользователей
сохраняются; это правило не даёт права продолжать выдачу после отзыва доступа
или согласия на соответствующую внешнюю обработку.

Правило применяется только после отдельно разрешённого бесплатного fallback.
Проверка бесплатности и согласие на передачу данных из RAG-31 сохраняются;
первичное внешнее переключение, платные модели и API-пробы не разрешаются
этим согласованием. №1–№6 приняты в MVP; №7 определяет поведение условного
маршрута, а не включает автоматический внешний fallback в MVP.

**Статус:** согласованное требование, не реализованная и не проверенная
возможность. При проектировании проверить поддержку границы выбранной интеграцией,
определить частоту и методику локальных проб, численные критерии скорости и
качества, а также поведение при ошибке провайдера и правила повторных попыток.
Согласование границы не гарантирует завершения ответа при отказе провайдера.

## Решение RAG-11: редакция 2026-10-09

По умолчанию сервис допускает до **12 активных запросов**. Каждый имеет отдельный
контекст и состояние формируемого ответа; данные разных пользователей не смешиваются.
Активный запрос участвует в продвижении генерации; запросы сверх лимита ожидают
в очереди допуска к активной обработке.

За один шаг генерации продвигаются до **3 активных запросов**: для каждого
вычисляется следующий токен, затем обслуживается следующая группа. Вычисления
распределяются справедливо между активными запросами, чтобы текст поступал
постепенно каждому, без ожидания завершения всего ответа другого пользователя.
Число 3 ограничивает число продвигаемых запросов за шаг, а не число активных ответов.

Оба дефолта, 12 и 3, задаются отдельным конфигурационным файлом и применяются
при запуске. Оба ограничения действуют на весь сервис, независимо от количества
API-процессов. Уполномоченный **super_admin** может менять каждое через админку;
изменения немедленно применяются без перезапуска. Правила авторизации и аудита
административных операций сохраняются.

**Статус:** согласованное требование, не реализованная и не проверенная возможность.
Эта документация не утверждает наличие нужного планировщика в llama.cpp.
При техническом проектировании требуется:

- Проверить поддержку выбранным runtime отдельных состояний, продвижения
  до 3 запросов за шаг, справедливого обслуживания и изменения ограничений на ходу.
- Измерить память для 12 контекстов с сохранением базового контекста запроса 4096,
  учитывая модель и остальные сервисы; измерить скорость постепенной выдачи,
  задержки и совместную нагрузку OCR/API/worker/PostgreSQL.
- При уменьшении лимита активных запросов соблюдать последующее RAG-49:
  уже активные продолжаются, новые ждут, пока число активных не станет меньше
  нового лимита. Технически определить применение меньшего размера следующей
  группы при изменении отдельного лимита продвижения запросов за шаг.
- Отдельно определить, где сохраняются изменения админки и какие значения
  используются после перезапуска: сохранённые настройки или значения файла.
  Политика сохранения и приоритет источников пока не согласованы.

Прежняя редакция 2026-10-03 — «3 активные генерации, остальные в очереди»,
лимит из файла при запуске — **заменена** этой редакцией. Она остаётся только
историческим решением в неизменённых исходных снимках и отчёте переноса.
Основание изменения: [заявка](../decisions/2026-10-09-generation-limits/request.md).

## Решения RAG-12/RAG-13/RAG-14: редакция 2026-10-09

**OCR рукописей включён в MVP.** Требование к OCR теперь охватывает печатный
и рукописный текст в PDF на русском, белорусском, английском и немецком языках.
Работа выполняется фоновым worker. Прежнее исключение рукописей заменено;
качество распознавания рукописей и ресурсная нагрузка ещё не проверены.

В данных **каждого пользователя** нужны отдельные поля разрешений:

- Добавление PDF.
- Добавление DOCX.
- Добавление TXT.
- Добавление Markdown.
- Использование OCR рукописей.

Разрешение OCR рукописей не заменяет разрешение загрузки формата файла.
Backend проверяет персональные разрешения, а не полагается на доступность
кнопок во frontend. Наличие поля или согласование требования не означает,
что механизм ограничения загрузок уже реализован.

**Все пять лимитов документов настраиваются отдельно для каждого пользователя.**
Начальные значения сохраняются как конфигурационные дефолты: 50 МБ на файл,
500 страниц на PDF, 20 файлов за загрузку, 1000 документов и 2 ГБ оригиналов.
МБ и ГБ — десятичные; квота оригиналов не включает индекс, OCR-данные и копии.
Backend должен учитывать персональные значения и параллельные загрузки;
уменьшение квоты не означает автоматического удаления сохранённых документов.

Персональные разрешения и лимиты нужны для **будущей раздельной тарификации**.
Тарифы, их привязка к полям и биллинг пока не выбраны; `paid` в MVP не проверяется.
При техническом проектировании определить точную схему полей, дефолты разрешений,
права изменения разрешений форматов/OCR, способ получения персональных значений из общих дефолтов
и применение изменений к уже начатой загрузке/обработке. Немедленное изменение
генерационных ограничений из RAG-11 не задаёт автоматически такую политику
для персональных документных лимитов.

**Административные права:** через админку глобальные динамические настройки
и лимиты может менять только `super_admin`. Обычный `admin` не имеет права
изменять глобальные значения, включая оба генерационных лимита RAG-11;
он может менять лимиты отдельных пользователей из RAG-13. Это право не даёт
доступа к их документам или перепискам. Backend проверяет права на каждой
операции и фиксирует административные изменения в аудите; скрытия кнопок недостаточно.
Право менять персональные лимиты не определяет автоматически, кто управляет
разрешениями форматов/OCR — это остаётся вопросом технического проектирования.

**Статус:** согласованные требования, не реализованные и не проверенные возможности.
Будущая приёмка включает разные разрешения и все пять лимитов двух пользователей,
запрещённый формат и запрещённое OCR рукописей через прямой API, пограничные
размеры/страницы/пачки/квоты, параллельные загрузки и качество OCR рукописей.
Для ролей проверить разрешённые глобальные изменения super_admin,
запрещённые глобальные изменения admin, разрешённые персональные изменения admin
и сохранение запрета на чтение чужих данных.
Основание изменения: [заявка](../decisions/2026-10-09-user-document-permissions-and-limits/request.md).

## Решение RAG-30: редакция 2026-10-09

Параметры моделей отображаются в административном интерфейсе **super_admin**.

контекста в пределах выделенной ёмкости и сама выделенная ёмкость runtime —
разные настройки; возможность менять первый не доказывает возможность менять
вторую без перезапуска. Базовые значения `-t 4 -tb 8`, контекст запроса 4096

**Статус:** согласованное требование, не реализованная и не проверенная возможность.
Проверить отображение обеих категорий, изменение разрешённых параметров без
перезапуска и отказ для заблокированных параметров через прямой API.
Основание: [заявка](../decisions/2026-10-09-model-settings-admin-availability/request.md).

## Решение RAG-31: редакция 2026-10-09

Если генерация переведена на разрешённую бесплатную внешнюю LLM, сервис
**периодически проверяет локальную модель**. Когда локальная LLM одновременно
проходит проверки **скорости и качества**, сервис **автоматически возвращает
генерацию на локальную LLM**. Успех только одного критерия не является основанием
для возврата. Эмбеддинги, поиск и состояние остаются локальными; смена LLM
не требует пересчёта эмбеддингов.

Проверка бесплатности внешнего маршрута и согласие на передачу вопроса,
фрагментов и истории сохраняются. Платные переключения запрещены.
Первоначальное включение внешнего маршрута остаётся отдельным решением;
новое требование определяет периодические проверки и обратный переход
после такого включения, а не разрешает запускать внешний fallback сейчас.

При техническом проектировании определить частоту проверок, порог/методику
измерения скорости, набор и метод проверки качества по согласованным критериям.
Граница возврата уточнена пользователем 2026-10-10 в RAG-39: начатый ответ
сохраняет свою модель, ожидающие и новые запросы выбирают актуальный маршрут
при допуске к генерации с повторной проверкой доступа и условий передачи данных.
Отзыв доступа или согласия имеет приоритет. Необходимо сохранить отдельные
контексты и состояния ответов пользователей и проверить поддержку этой границы;
поведение при ошибке провайдера и повторных попытках ещё не определено.

**Статус:** согласованное требование, не реализованная или проверенная возможность.
Фактические локальные пробы, внешний API и отложенная проверка GLM этим поручением
не запускаются. Основание: [заявка](../decisions/2026-10-09-local-llm-return/request.md).

## Решение RAG-40: отмена при отключении, 2026-10-13

возможность. Сохранение частичного ответа определено в RAG-41, граница вкладок —
в новой редакции RAG-43, включая ожидание 10 секунд. Обнаружение отключения ещё проектируется;
автоматическое возобновление отменённого запроса не разрешено.

## Решение RAG-41: сохранение прерванного ответа, 2026-10-13

## Решение RAG-42: синхронизация вкладок одной беседы, 2026-10-13

Основание — явное поручение пользователя «зафиксируй этот вариант в brainstorm»
с приведённым сценарием двух разных вопросов в двух вкладках.

У беседы одна история на сервере, которую показывают все её вкладки.
Ещё не отправленный вопрос остаётся отдельным черновиком каждой вкладки.

1. Вкладка A отправляет вопрос. Сервер принимает его и отмечает беседу занятой
   с момента принятия до завершения или отмены запроса, включая ожидание в очереди.
2. Вкладка B получает обновление, показывает принятый вопрос и поступающий ответ,
   блокируя отправку своего вопроса.
3. Если B отправила другой вопрос до получения обновления, сервер отказывает:
   «В беседе уже выполняется запрос». Второй вопрос остаётся в поле ввода B.
4. После завершения или отмены первого запроса обе вкладки обновляют историю;
   отправка снова доступна. Следующий вопрос учитывает завершённый первый ответ;
   прерванный ответ остаётся исключённым из контекста по RAG-41.

При почти одновременной отправке разных вопросов сервер атомарно принимает
только один. Второй не добавляется в историю и не ставится в очередь вопросов
этой беседы. Вкладки получают уведомления о серверном состоянии; SSE приведён
как пример транспорта синхронизации, конкретный механизм ещё проектируется.

**Статус:** согласованное требование MVP, не реализованная и не проверенная
возможность. Отмена при отключении уточнена в RAG-43.
Удаление черновиков при закрытии вкладки уточнено последующим RAG-48.

## Решение RAG-43: отключение отправившей вкладки и ожидание 10 секунд, 2026-10-13

В боковом обсуждении пользователь поручил «зафиксируй это и вариант 1» после
разбора отмены по отправившей вкладке и варианта ожидания восстановления 10 секунд.
Эта редакция заменяет ранее выбранную отмену по последней подключённой вкладке.

После обнаружения отключения вкладки, отправившей вопрос, сервер ждёт 10 секунд,
даже если другие вкладки этой беседы подключены. Ожидающий запрос сохраняет место
в очереди; начатая генерация продолжается, текст сохраняется на сервере.
Если инициирующая вкладка восстановила соединение до истечения срока, отмена
снимается: она получает накопленный текст и продолжение того же запроса без
повторной отправки вопроса. Другие открытые вкладки сами по себе не снимают отмену.

Если соединение инициирующей вкладки не восстановлено за 10 секунд, незавершённый
запрос отменяется для всех вкладок, очередь или слот освобождается. Частичный текст
остаётся с отметкой «Прервано» и исключается из последующего контекста по RAG-41.
Остальные вкладки показывают отмену и разблокируют отправку; их отдельные черновики
сохраняются по RAG-42. Если ответ завершился во время ожидания, он сохраняется как
обычный завершённый ответ. Уже отменённый запрос после возвращения не возобновляется.

Ожидание относится к отключению соединения; кнопка «Остановить» по RAG-26 и
прекращение доступа по RAG-23 не откладываются на эти 10 секунд.

**Статус:** согласованное требование MVP, не реализованная и не проверенная
возможность. Способ обнаружения отключения и идентификации восстановленной
инициирующей вкладки ещё проектируется; во время ожидания запрос занимает ресурсы.

## Решение RAG-44: ошибка локальной генерации, 2026-10-13

Пользователь выбрал вариант 1 вместо одного автоматического повтора генерации.
Сервис показывает ошибку, освобождает ресурсы и беседу; новый вопрос отправляет
сам пользователь. Частичный текст сохраняется как прерванный и исключается
из контекста последующих ответов, включая checkpoints и резюме.

Если ошибка произошла до первого токена, частичного ответа нет; ошибка всё равно
завершает запрос и освобождает беседу. Во всех её вкладках отправка снова доступна,
отдельные черновики сохраняются по RAG-42. Ожидание восстановления соединения по
RAG-43 не откладывает обработку ошибки и не возобновляет завершившийся ошибкой запрос.
Внешний fallback этим решением не разрешается.

**Статус:** согласованное требование MVP, не реализованная и не проверенная возможность.

## Решение RAG-45: переключение между беседами, 2026-10-13

Пользователь выбрал вариант 1 вместо немедленной отмены при переходе из беседы
A в B в той же открытой вкладке. Запрос A сохраняет свой жизненный цикл и
продолжает ожидать или генерироваться в фоне; результат принадлежит беседе A.
При возвращении в A отображаются её текущий результат и состояние запроса.

Переключение беседы не считается обрывом инициирующей вкладки и не запускает
ожидание отмены RAG-43. Реальное отключение соединения по-прежнему обрабатывается
по RAG-43; остановка, ошибка и прекращение доступа сохраняют свой приоритет.
Фоновый запрос учитывается в общих лимитах RAG-11.

**Статус:** согласованное требование MVP, не реализованная и не проверенная возможность.

## Решение RAG-46: черновики при переключении бесед, 2026-10-13

Пользователь выбрал вариант 1 вместо очистки неотправленного текста при переходе
из беседы A в B. В пределах одной вкладки каждая беседа сохраняет свой черновик;
возвращение в A восстанавливает её текст в поле ввода, без отправки вопроса.
Черновики A и B не подменяют друг друга; разные вкладки остаются независимыми
по RAG-42. Черновик не становится сообщением истории до отправки и приёма вопроса.

**Статус:** согласованное требование MVP, не реализованная и не проверенная
возможность. Сохранение после перезагрузки страницы уточнено последующим RAG-47;
удаление при закрытии вкладки уточнено последующим RAG-48.

## Решение RAG-47: черновики после обновления страницы, 2026-10-13

Пользователь выбрал вариант 1: обновление страницы в той же вкладке сохраняет
набранные неотправленные тексты. Каждая беседа сохраняет свой черновик по RAG-46;
при открытии соответствующей беседы её текст восстанавливается в поле ввода.
Восстановление не отправляет вопрос и не добавляет сообщение в историю.
Черновики других вкладок остаются независимыми по RAG-42.

Это решение касается черновиков; выполняющийся запрос при реальном обрыве
соединения во время обновления страницы по-прежнему подчиняется RAG-43.
Удаление при закрытии вкладки уточнено последующим RAG-48.
Способ хранения черновиков остаётся вопросом технического планирования.

**Статус:** согласованное требование MVP, не реализованная и не проверенная возможность.

## Решение RAG-48: черновики при закрытии вкладки, 2026-10-13

Пользователь выбрал вариант 1: закрытие вкладки удаляет её неотправленные
черновики всех бесед. При следующем открытии приложения эти тексты не
восстанавливаются. Переключение бесед и обновление страницы в той же вкладке
сохраняют черновики по RAG-46/RAG-47; закрытие завершает срок их хранения.

Черновики остальных открытых вкладок сохраняются независимо по RAG-42.
Серверная история принятых сообщений сохраняется по RAG-25. Выполняющийся
запрос при отключении закрытой вкладки следует RAG-43, включая ожидание
10 секунд; удаление черновика не меняет политику отмены запроса.
Способ различения обновления страницы и закрытия вкладки остаётся вопросом
технического планирования.

**Статус:** согласованное требование MVP, не реализованная и не проверенная возможность.

## Решение RAG-49: уменьшение лимита активной генерации, 2026-10-13

Пользователь выбрал вариант 1: уже активные запросы продолжают свой жизненный
цикл при уменьшении лимита. Изменение лимита само по себе не отменяет их и не
приостанавливает. Новые запросы остаются в очереди допуска, пока число активных
не станет строго меньше нового лимита. Это уточняет открытый вопрос RAG-11.

Пример: при 10 активных запросах лимит меняется на 6. Все 10 продолжаются;
при 6 активных новые ещё ждут, при 5 может быть допущен один новый запрос.
Временное превышение нового лимита допустимо для ранее активных запросов,
а дальнейший допуск соблюдает новый предел. Освобождение мест при завершении,
остановке, ошибке, обрыве связи и прекращении доступа подчиняется действующим
правилам; выбор не обещает успешного завершения каждого запроса.

Решение касается числа активных запросов; отдельный лимит продвижения за шаг,
его техническое применение и политика сохранения настроек после перезапуска
этим выбором не уточняются. Фактическую поддержку требуется проверить в runtime.

**Статус:** согласованное требование MVP, не реализованная и не проверенная возможность.

## Дополнительные явные требования пользователя

- Multilingual с обязательным русским для LLM и эмбеддингов. Прямая реплика сохранена
  в [стенограмме](../testing/evidence/2026-10-08-rag-decision-import/_docs/conversation_transcripts/conversation-transcript-2026-10-02.md).
  Поддержка языка по карточке модели не доказывает качество RAG на документах.
- Стенограмма — архив для пользователя; не загружать её при каждом старте.
- Прежний проект использовал Python 3.12.15, `.venv31215`, `uv sync --locked`.
  Это настройки источника, а не уже созданное окружение назначения. Общие правила
  текущего harness требуют uv; окружение и зависимости здесь не установлены.
- Новые продуктовые вопросы задавать по одному. Ранее согласованные решения
  не открывать заново без новых оснований.

## Уточнения уже выбранной архитектуры

- Ссылки ответа должны указывать доступный источник и фрагмент; при недостатке
  оснований сообщать об этом. Смена LLM не требует переиндексации; смена модели
  эмбеддингов требует пересчёта. Для E5 используются query:/passage:, masked mean
  pooling, L2-нормализация, 384 измерения и предел 512 токенов с префиксом.
- Полная история отделена от окна модели. Для одной беседы — один активный запуск;
  повторы одной операции не дублируют сообщения. Прерванный ответ не считается
  завершённым; сохраняется в истории и исключается из последующего контекста по
  RAG-41. Удалённый материал не восстанавливается из исторических checkpoints.
- Подробные правила повторов загрузки, частичного успеха пачки, обрыва соединения,
  удаления во время генерации и административного чтения сохранены в источниках.
  Текущее правило обрыва соединения задаёт RAG-40; прежнее продолжение запроса
  из импортированного источника заменено новым выбором пользователя.
  Разделы с предложениями не превращены в новые утверждённые пользователем решения.

## Пока не утверждено

Библиотека аккаунтов (FastAPI Users — кандидат), серверные cookie-сессии,
frontend-фреймворк, SQLAlchemy/async-драйвер и миграции, очередь (Celery/Redis —
кандидат), парсеры/OCR, рабочее хранилище оригиналов, SMTP, команды развёртывания,
ёмкость/срок ожидания очереди, численный порог задержки, политика уменьшения
лимитов RAG-11 на ходу и сохранения изменений админки после перезапуска.
Для RAG-12/RAG-13 также не определены схема персональных полей, дефолты разрешений,
права изменения разрешений форматов/OCR, связь с тарифами и применение к незавершённым операциям.
Для RAG-31 не определены частота повторных локальных проверок, критерии/методика
скорости и качества для возврата, поведение при ошибке провайдера и повторных попытках.
Граница возврата для начатых и ожидающих ответов согласована в RAG-39;
поддержка интеграцией ещё не проверена. Для RAG-33–RAG-38 остаются открыты
детали доставки фрагментов и интерфейса, связывание выводов с источниками,
происхождение OCR-правок, индексация и старые цитаты, состав оценок последствий,
стоимость проверки PDF и качество поиска противоречий.
Путь и формат `backend/config/runtime.toml` предложены; утверждены отдельный файл
с дефолтами при запуске и немедленное изменение обоих лимитов через админку.
OIDC/SSO, SQLAdmin и Starlette Admin
сохранены как рассмотренные альтернативы, а не выбранный путь.

## Границы MVP и отсрочки

Биллинг и проверка paid, физическое удаление аккаунтов, PWA/мессенджеры,
организации/команды/общие библиотеки, платные модели и автоматический внешний
fallback в MVP не включены. GLM отложена до необходимости fallback. Автономные
действия агента, web-поиск и междиалоговая персональная память не утверждены.
Автоматическая перепроверка старых ответов, предварительная стоимость запроса
и тарифные счётчики также отложены в исходной проверке идеи.

## Известные ограничения свидетельств

- Замеры 2026-10-02 — один слот, синтетические русские сценарии, без полного
  портала, OCR, PostgreSQL/pgvector, LangGraph и проверки пользовательских прав.
- Qwen3.5-2B выбрана по совокупности этих проб; Qwen3-1.7B не прошла длинный
  сценарий; 4B прошла ответы, но вызвала давление на память/swap.
- 30/30 реальных вопросов, совместная работа 10 пользователей и новая модель
  12 активных запросов / до 3 продвигаемых за шаг, OCR четырёх языков,
  восстановление и достаточность 4096 токенов не проверены. Память для 12 контекстов
  и скорость выдачи выбранным runtime также не проверены.
- OCR рукописей, персональные разрешения форматов/рукописей и все пять
  индивидуальных лимитов документов не реализованы и не проверены.
- Периодические проверки локальной LLM во время бесплатного fallback и
  автоматический возврат при прохождении скорости и качества не реализованы и не проверены.
- Сведения о 5,6 GiB WSL, времени ответа и бесплатных API — исторические.
  Текущие ресурсы/квоты/цены не перепроверялись. Перед fallback нужны новая
  проверка бесплатности и согласие на внешнюю передачу вопроса, фрагментов и истории.
- Копии на том же диске не защищают от отказа диска. Архивные скрипты не запускались;
  веса и окружение из `/tmp/rag-model-probe` не перенесены и могут отсутствовать.
