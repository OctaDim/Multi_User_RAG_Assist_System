## Что реализовано в образце

Пути этого раздела относительны корню TLT_TG_AggregatorManager.

1. `db_postgres/postgres_conn/pgs_connection.py`: отдельные sync/async engines с пулом, pre-ping, recycle и timeout. `SingletonMeta` кэширует объект по классу; URL собирается f-строкой из отдельных реквизитов.
2. `db_postgres/postgres_conn/postgres_session.py`: собственные контекстные менеджеры создают sessionmaker, открывают сессию, выполняют commit/rollback при выходе и затем закрывают сессию. `expire_on_commit=False`, `autoflush=False`.
3. `db_postgres/postgres_init/declarative_base_model.py`: единый `Base = declarative_base()`.
4. `postgres_models/auth_role_model.py` и `telethon_configs_model.py`: модели в отдельных модулях, `Mapped`/`mapped_column`; общие поля вынесены в `orm_models_fields_mixins.py`.
5. `postgres_init/db_tables_init_imports.py`: явные импорты регистрируют модели в metadata. `db_tables_initialization.py` проверяет доступность БД и вызывает `metadata.create_all` через `DBTablesManager`.
6. `main.py:275`: инициализация таблиц вызывается в запуске основного скрипта. Lifespan создаёт пользователей, а при завершении освобождает оба engine. Само определение функции не обеспечивает её вызов при любом способе запуска ASGI-приложения.
7. `postgres_queries_utils/create_where_partial_query.py`: функция получает существующий Select и добавляет условия equality, IS, IN и сочетание IN с NULL.
8. `postgres_queries_utils/create_order_partial_query.py`: добавляет сортировку к уже собранному запросу.
9. `postgres_queries_utils/get_model_records_flex_query.py`: select модели/колонок → дополнение WHERE → дополнение ORDER BY → execute → scalars/all.
10. `postgres_queries/`: предметные функции чтения и обновления конфигураций; часть принимает текущую сессию, часть открывает собственную.
11. `requirements.txt:56`: SQLAlchemy 2.0.46; используются asyncpg и psycopg2. Alembic и файлы его окружения не обнаружены поиском по доступному дереву проекта.

Переносимая основа: отдельные модели, единая metadata, engine с пулом, сессия/транзакция ограниченного времени жизни, предметные query-функции и композиция SQLAlchemy expressions. Полное копирование всех универсальных помощников не требуется для этих принципов.

## Подтверждённые проблемы и предлагаемые изменения

### 1. Закрытие сессии при ошибке commit/rollback

`postgres_conn/postgres_session.py:30–64`: при ошибке commit выполняются rollback и raise; до нижнего блока close выполнение не доходит. Ошибка rollback также прерывает закрытие. Проверка `is_active` не является проверкой того, закрыта ли сессия. Аналогичная структура у sync-менеджера.

Предложение: стандартные контекстные менеджеры `async_sessionmaker` и транзакции; фабрику создавать один раз для engine, сессию — на операцию. Query-функции принимают текущую сессию и не выполняют скрытых commit. Параллельные задачи получают разные сессии.

Основание: [SQLAlchemy async sessionmaker.begin](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#sqlalchemy.ext.asyncio.async_sessionmaker.begin) описывает предоставление сессии, commit и close в одном контекстном менеджере. Это предложение ещё не проверено в RAG.

### 2. Ошибки могут раскрывать сохраняемые данные

`postgres_queries_utils/get_model_records_flex_query.py:96–105` включает фильтры и текст исключения в HTTPException.detail. `create_cache_new_model_object.py` и `postgres_queries/qry_cache_new_telethon_config_obj.py` аналогично включают новые данные. Модель Telethon содержит токены и строки сессий: при соответствующей ошибке они могут попасть в ответ или лог.

Предложение: слой БД не формирует HTTP-ответы; API преобразует ожидаемые ошибки в существующие публичные коды. Логи не содержат паролей, токенов, DSN и полных словарей данных; SQLAlchemy engine скрывает параметры в диагностике. Это не утверждение, что утечка уже происходила.

### 3. Массовые обновления загружают объекты

`postgres_queries_utils/update_existing_model_objects.py:20–33` сначала получает все ORM-объекты, затем для каждого вызывает helper с merge. Для одинакового изменения выбранных строк это лишняя загрузка и обход объектов; точное число SQL-команд зависит от состояния сессии и flush, оно не измерялось.

Предложение: `update(Model).where(...).values(...).returning(...)` для подходящих массовых операций; add/flush для новых объектов. Сохранить построчную бизнес-логику там, где требуется отдельное событие, аудит или переход состояния. Не заменять массовым UPDATE проверки прав или правила жизненного цикла.

### 4. Универсальный helper скрывает форму результата

`get_model_records_flex_query.py`: при selected_fields из нескольких колонок и `return_scalars=True` результат содержит только первую колонку. `distinct_on` принят async-функцией, но не применяется. Аннотация `Query` в WHERE-helper импортирована из FastAPI, хотя функция строит SQLAlchemy Select. Конвертеры `convert_orm_rows_to_dict.py` копируют `__dict__`, включая служебное ORM-состояние.

Предложение: использовать предметные функции, возвращающие `Select`, выражения фильтра или подзапрос; явно выбирать `scalars()` для модели/одного столбца и `mappings()` для нескольких полей. Сериализовать только явно выбранные поля. Не переносить неиспользуемые аргументы и строковый универсальный язык запросов.

### 5. Singleton и ручная сборка URL усложняют жизненный цикл

`meta_classes/singlton_meta.py` учитывает только класс, поэтому повторный вызов класса с другим DSN не создаёт другой объект. `pgs_connection.py` формирует URL из необработанных реквизитов, что требует корректного кодирования специальных символов. Это потенциальные ограничения, не воспроизведённые инциденты.

Предложение: engine принадлежит lifespan конкретного процесса; фабрика принимает DSN явно; `make_url`/`URL.create` для корректной работы с URL. Сохранить установленный psycopg 3 как SQLAlchemy-драйвер, если проверки подтвердят совместимость; дополнительный asyncpg без необходимости не добавлять. Отдельное удерживаемое соединение оставить для session-level advisory lock, не возвращать его в общий пул до освобождения блокировки.

### 6. create_all не заменяет миграции

`db_tables_manager.py` вызывает create_all; ручная проверка существования выполняет отдельный запрос на каждое имя и не ограничивает schema. `db_tables_initialization.py` при недоступной БД лишь печатает ошибку.

Предложение: единый путь инициализации через Alembic до готовности приложения/воркеров, сериализация одновременных запусков PostgreSQL advisory lock. Чистая БД автоматически получает таблицы и остальные объекты через миграции; повторный старт идемпотентен. Ошибка подготовки схемы прерывает старт.

`create_all` создаёт отсутствующие таблицы, но не обновляет существующие и не заменяет миграции: [SQLAlchemy metadata / migrations](https://docs.sqlalchemy.org/en/20/core/metadata.html#altering-database-objects-through-migrations). [Alembic cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html#building-an-up-to-date-database-from-scratch) допускает create_all + stamp для bootstrap; для RAG этого недостаточно без учёта view, trigger, extension и начальных данных. Здесь предлагается один путь через Alembic.

Отдельная граница для согласования: обычное создание новой схемы/таблиц миграциями и восстановление вручную удалённой таблицы при уже установленном head — разные операции. Предлагается при таком повреждении остановить старт с диагностикой, а восстановление проводить явно через Alembic. Простое создание пустой таблицы не восстанавливает утраченные данные. Пользователь утвердил остановку при повреждении актуальной схемы.

### 7. Дополнительные замечания по образцу

- `orm_models_fields_mixins.py` использует локальное `datetime.now` без timezone. В RAG уже используются timestamptz и серверное время; сохранить их.
- `merge_obj_ongoing_session.py` пересоздаёт исключение через `type(error)(log_error)`; у исключений SQLAlchemy могут быть другие аргументы конструктора. Сохранять исходное исключение обычным raise.
- `postgres_tests/` содержит ручные примеры под `if __name__ == '__main__'`; два ссылаются на отсутствующий в найденном дереве `__temp.webhook_conversation_model`. Это не доказательство корректности транзакций. Тесты образца не запускались.
- Размеры пула 20 + 30 из `configs/options.py` не переносить автоматически: у RAG несколько процессов, каждый со своим пулом. Настройка требует учёта общего числа соединений.

## Существенная развилка: LangGraph

Проверен исходник установленной зависимости `backend/.venv/lib/python3.12/site-packages/langgraph/checkpoint/postgres/{aio,base}.py`.
`setup()` выполняет собственный список DDL-миграций; get/list/put/writes выполняют SQL через psycopg. Перенос этих вызовов за оболочку SQLAlchemy не превращает запросы в SQLAlchemy expressions.

### Вариант A: буквальное выполнение требования для всех управляемых запросов

SQLAlchemy-модели и expressions охватывают приложение, SQL-запросы в тестах и хранение checkpoint. Для LangGraph реализуется совместимый saver через SQLAlchemy с сохранением существующей сериализации, namespace, версий, pending writes, порядка записей, фильтров, owner/epoch guards и данных. Все схемные изменения, включая checkpoint, выполняет Alembic; `.setup()` стороннего saver не вызывается.

Плюс: единый путь запросов и миграций. Цена: поддержка совместимости saver с LangGraph становится обязанностью проекта. Нужны контрактные проверки, а не только CRUD. Рекомендуется, если «все запросы» включает checkpoint без исключения.

### Вариант B: явное исключение для штатного checkpointer

Модели и SQLAlchemy expressions охватывают приложение; сохраняется официальный AsyncPostgresSaver и его внутренний SQL. Его DDL переносится под контроль Alembic, runtime setup запрещается. Проверки доступа и запись должны остаться в одной физической транзакции; адаптацию общей connection необходимо доказать тестами.

Плюс: меньше собственного кода и сохранение штатной реализации checkpoint. Цена: это исключение из буквального «все запросы через SQLAlchemy», а также совместимость соединения/миграций с установленной версией библиотеки. Пользователь явно выбрал этот вариант Б; исключение зафиксировано в требованиях.

Оба варианта включают исправления пунктов 1–6 выше; DDL PostgreSQL для extension, view, trigger/function при необходимости остаётся текстом исключительно внутри Alembic-ревизий. Рабочие SELECT/INSERT/UPDATE/DELETE должны строиться выражениями SQLAlchemy в согласованной области.

## Дополнение 2026-10-15: создание connection и session

Пользователь отдельно попросил рассмотреть организацию создания connection/session в образце и предложить улучшенные варианты. Ниже сохранено сравнение рассмотренных вариантов. Выбран вариант 2 с классом Database; для LangGraph выбран вариант Б со штатным saver.

### Фактическая последовательность в образце

- `db_postgres/postgres_conn/pgs_connection.py:24–58`: `PgsAsyncConnection` — singleton-владелец AsyncEngine. Вызов класса получает/создаёт engine с пулом, а не выделяет физическое соединение на каждый запрос.
- Там же, строки 64–68: health check отдельно получает connection через `engine.connect()`. Создание engine само по себе не подтверждает доступность PostgreSQL.
- `db_postgres/postgres_conn/postgres_session.py:7–25`: каждый новый `PgsAsyncSession(engine)` создаёт новый `async_sessionmaker`; вход в контекст создаёт AsyncSession. `__aexit__` управляет commit/rollback/close вручную.
- `postgres_queries/qry_cache_new_telethon_config_obj.py:16–29`: предметная функция сама получает singleton и открывает сессию. Её внутренний helper принимает уже открытую сессию.
- `telethon_manager/telethon_clients_manager.py:46–56` и `fast_api/app_messages_configs_by_web_acc/router_messages_configs_by_web_acc.py:65–73`: внешний вызывающий код открывает сессию и передаёт её query-функции. Этот способ проще объединяет несколько запросов в одну транзакцию.
- В образце одновременно используются оба подхода к владению сессией. Для RAG нельзя автоматически переносить открытие отдельной сессии внутрь каждого запроса: уже существуют составные операции с общими блокировками, проверками прав и записью результатов.

### Предлагаемые сроки жизни

| Объект | Кто создаёт | Когда освобождается |
|---|---|---|
| AsyncEngine и его пул | Отдельная фабрика при старте API/воркера/CLI, один экземпляр на используемую БД в процессе | После остановки и ожидания фоновых задач; `await engine.dispose()` в finally |
| async_sessionmaker | Отдельная функция один раз для данного engine | Вместе с владельцем engine |
| AsyncSession | Контекст на отдельную бизнес-операцию | При выходе из контекста; успешная запись фиксируется, исключение приводит к откату |
| Обычный connection | Пул engine выдаёт при необходимости, часто через сессию | Возвращается в пул после завершения работы |
| Connection с session-level advisory lock | Supervisor/воркер явно удерживает выделенное соединение | После остановки защищаемой работы и освобождения lock; потеря соединения означает потерю владения |

Один engine на процесс не означает один общий объект Session или одно соединение для всех запросов. AsyncSession не разделяется между одновременно выполняющимися asyncio-задачами. Документация: [ленивое подключение engine](https://docs.sqlalchemy.org/en/20/core/engines.html#engine-configuration), [AsyncSession и конкурентные задачи](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks).

### Вариант 1: отдельные функции и штатные контексты — рекомендация

Разделить конфигурацию engine и создание фабрики сессий по модулям. Внешняя функция бизнес-операции выбирает границу транзакции; вложенные query-функции получают session аргументом и не закрывают её, не выполняют commit самостоятельно. Для явного connection использовать штатные `engine.connect()`/`engine.begin()`; отдельный helper нужен только там, где есть дополнительная обязанность, например захват и освобождение advisory lock.

Пример предлагаемого интерфейса, не реализованный код приложения:

```python
from contextlib import asynccontextmanager
from sqlalchemy.ext.asyncio import async_sessionmaker


def create_session_factory(engine):
    return async_sessionmaker(engine, expire_on_commit=False)


@asynccontextmanager
async def session_scope(session_factory):
    async with session_factory.begin() as session:
        yield session
```

`session_scope` — небольшой единый вход, если нужен собственный именованный интерфейс, как в образце. Без такого требования допустимо напрямую использовать `session_factory.begin()` с тем же поведением и меньшим числом функций. В обоих случаях commit/rollback/close выполняют штатные контексты SQLAlchemy, а не копия ручного `__aexit__`.

Функция `create_db_engine(dsn)` отдельно настраивает PostgreSQL/psycopg, пул и скрытие параметров. DSN нормализуется без f-строк из отдельных секретов; фабрика вызывается в lifespan, не на каждый запрос и не при импорте модуля. Lifespan обязан освобождать engine также при ошибке миграции/старта. Порядок: создать engine → подготовить схему Alembic → запустить работу → остановить/дождаться задач → dispose.

Плюсы: простая структура, близкая к разделению conn/session/query в образце; штатная обработка транзакций; удобная подмена DSN в тестах без singleton. Цена: engine и фабрика передаются явно через состояние приложения и параметры воркеров. Не следует добавлять отдельные универсальные классы repository/unit-of-work без предметной необходимости.

### Вариант 2: небольшой объект Database без singleton

Собрать engine и session_factory в одном объекте, передаваемом в API/воркеры. Методы создания session/connection возвращают штатные контексты SQLAlchemy; lifecycle управляет dispose. Объект создаётся явно, допускает несколько независимых тестовых БД, не хранит общую текущую сессию.

Плюсы: один передаваемый объект и организация, более похожая на классы образца. Цена: дополнительная оболочка над engine/sessionmaker; для нынешней конфигурации с одной БД существенного преимущества над функциями не видно. Корректность транзакций и работа пула такие же, сама оболочка ускорения не даёт.

### Что сохранить при любом варианте

- Отдельная короткая транзакция на атомарную операцию; не удерживать одну сессию на всю SSE-подписку, OCR или генерацию ответа. Существующие короткие защищённые операции остаются защищёнными.
- До выдачи успешного HTTP-ответа записывающая операция уже должна завершить commit. Не полагаться на отложенный commit при финализации длительной stream-зависимости FastAPI.
- Проверка владельца/epochs и связанная запись checkpoint выполняются на одном соединении внутри общей транзакции; решение A/B не должно разорвать эту границу.
- Для advisory lock — удержание физического соединения на весь период владения. Возвращать его в пул с неосвобождённой session-level блокировкой нельзя; при неопределённом состоянии соединение инвалидируется.
- `expire_on_commit=False` не обновляет автоматически устаревшие данные и не разрешает ленивую загрузку после закрытия сессии. API возвращает явно подготовленные данные; авторизация проверяется заново в каждой необходимой операции.
- `pool_pre_ping` выявляет неисправное соединение при выдаче из пула, но не восстанавливает прерванную транзакцию. Автоматически повторять неидемпотентную запись после неизвестного результата commit нельзя.

Выбор между вариантами 1/2 касается организации connection/session; он не заменяет отдельное согласование остальных предложений и LangGraph A/B. Примеры не запускались; SQLAlchemy ещё не установлен в рамках этой задачи.
