## Изменение контракта U3 / KTD5–KTD6

Вместо двух укрупнённых начальных ревизий создаётся единая последовательная цепочка: шесть ревизий Alembic соответствуют прежним SQL 001–006, следующая управляет checkpoint-схемой штатного saver. Таблицы, индексы и ограничения исторических шагов описываются Alembic operations; изменения данных — выражениями SQLAlchemy. SQL для PostgreSQL view/function/trigger остаётся внутри версионируемых ревизий.

Пустая БД проходит всю цепочку Alembic; новый legacy-журнал ей не нужен. Для существующей БД прежние имена и SHA256 проверяются вместе с точным состоянием схемы соответствующего префикса. Только успешная проверка разрешает установить соответствующую позицию Alembic и применить оставшиеся ревизии. Уже выполненные преобразования данных не повторяются. Существующий lifecycle_migrations сохраняется как историческое свидетельство; дальнейшие версии учитывает только Alembic.

Старый SQL-runner и выполнение суффикса .sql при запуске исключаются. Старые файлы доступны в Git для проверки происхождения; они не являются вторым исполняемым механизмом миграций. Начальная и последующие подготовленные ревизии должны работать через один upgrade head; запуск не генерирует ревизии.

## Проверки

Проверить пустую БД, каждый из шести прежних префиксов, полную старую БД и повторный запуск. Сохранить доказательства переноса lease из 003 и однократного завершения старых запросов в 005. Привязка к Alembic запрещена при неизвестной/разорванной истории, неверной контрольной сумме либо несовпадающей схеме. Проверить новую подготовленную ревизию после текущего head без изменения замороженных исторических контрактов.

Все остальные требования исходного плана сохраняются, кроме порядка проверки качества: последним уточнением пользователь полностью исключил проверку 30/30 ответов и цитат из этой задачи, в том числе после заключительных коммитов. Технические проверки доступа к источникам и целостности цитат остаются обязательными.
