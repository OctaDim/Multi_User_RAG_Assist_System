# Запуск бэка и фронта

После подготовки окружения и конфигов из корня проекта:

```bash
python3 backend/main.py
python3 frontend/main.py
```

Каждую команду запускайте в своём терминале. `Ctrl+C` или SIGTERM останавливает соответствующий раздел и все принадлежащие ему процессы. У фронта нет дочерних сервисов: завершаются HTTP-сервер и его потоки. PostgreSQL работает независимо и при остановке приложения остаётся запущенным. Бэк останавливает все запущенные им процессы, включая native worker модели; если один компонент неожиданно завершился, весь запуск завершается с ненулевым кодом.

Из другого рабочего каталога укажите абсолютный путь к main.py. Относительные пути внутри конфигов по-прежнему отсчитываются от `backend/` или `frontend/`.

## Однократная подготовка

1. Нужны Python 3.12 для бэка и установленный `uv`. Main проверяет окружение до импортов приложения; отсутствующие Python-зависимости восстанавливает через `uv` по `backend/uv.lock`, затем проверяет результат. Явная подготовка: `uv sync --project backend --frozen`. Фронту достаточно Python 3.11+ и стандартной библиотеки; Node.js и сборка не нужны.
2. PostgreSQL с pgvector устанавливается отдельно. В текущей WSL установлен PostgreSQL 16 с pgvector 0.6.0 из пакетов Ubuntu: `postgresql-16`, `postgresql-client-16`, `postgresql-16-pgvector`. Кластер `16/main` слушает `127.0.0.1:5432` и включён в systemd. Созданы база `rag_assist` и её владелец `rag_assist_user` без прав суперпользователя, создания БД и ролей. Администратор заранее установил расширение `vector` в этой базе; готовые ревизии Alembic применяются приложением при старте.
3. Полный модельный набор хранится в `rag/local_models/` относительно корня проекта, вне Python-окружений. Manifest `backend/config/models.toml` закрепляет девять файлов, SHA-256, источники, immutable revisions и совместимые профили. Подготовка выполняется явно:

   ```bash
   # Перенести существующий полный набор после проверки исходников и назначения:
   python3 backend/prepare_models.py --source /path/to/existing-models --move

   # Либо явно скачать весь закреплённый набор:
   python3 backend/prepare_models.py --download
   ```

   Скачивание идёт в staging; набор выбирается только после проверки всех файлов. Повреждённое существующее назначение не перезаписывается автоматически. Без `--move` источник сохраняется; с `--move` удаляются только проверенные companions после проверки назначения. Неизвестные файлы источника сохраняются. Подготовка не меняет модели, embedding space или preprocessing; замена набора требует отдельной проверки совместимости и отката.
4. Для новой установки скопируйте `backend/config/service.local.example.toml` в `backend/config/service.local.toml`, заполните постоянный DSN и фактические пути. В текущей установке этот приватный файл уже подготовлен с правами `0600`: пути указывают в `../rag/local_models/`, пароль БД не хранится в Git. SMTP настраивается отдельно для регистрации с подтверждением email; при пустой SMTP-конфигурации отправка подтверждений недоступна.
5. Фронт по умолчанию работает на `http://127.0.0.1:8080` и обращается к API `http://127.0.0.1:8000`. Для других адресов используйте `frontend/config/service.local.toml` и согласуйте его с `api.frontend_origin` бэка.

Обычный main проверяет наличие и SHA-256 обязательных моделей, совместимость профилей и runtime до старта компонентов. Он не скачивает веса, не устанавливает системный PostgreSQL и не подменяет постоянную установку временными тестовыми значениями. Ошибка называет недостающий ресурс и явную подготовку.

Крупные модельные файлы, tokenizer/JSON companions, staging и backups исключены из Git. Scaffold `rag/local_models/.gitignore`, manifest и код подготовки отслеживаются. Удаление или пересоздание virtualenv не удаляет модельные ресурсы.

## Источники настроек

Каждый раздел читает общий `config/service.toml`, затем локальный `config/service.local.toml`, если он существует. Переопределения объединяются по ключам секций; неизвестный ключ считается ошибкой. Общие конфиги и шаблоны хранятся в Git. Рабочие `service.local.toml` исключены точными правилами `.gitignore`.

Альтернативный файл локальных переопределений можно передать через `--config /path/to/settings.toml`; он заменяет стандартный локальный файл, а не общий конфиг. Бэк также поддерживает селектор `RAG_SERVICE_CONFIG` для совместимости отдельных компонентов; `--config` имеет приоритет. Эффективный путь передаётся детям абсолютным, до смены рабочего каталога.

Launcher бэка формирует существующие `RAG_DATABASE_URL`, `RAG_MODEL_PATH`, `RAG_E5_DIR`, `RAG_OCR_DIR`, `RAG_OCR_MODEL_PATH`, `RAG_ORIGINALS_DIR`, `RAG_FRONTEND_ORIGIN` и SMTP-переменные из конфигурации. Эти значения имеют приоритет над одноимёнными унаследованными переменными. Существующие отдельные `rag-api`, `rag-generation`, `rag-documents` и тестовые component entrypoints сохраняются и продолжают поддерживать свой env-интерфейс.

### Бэкенд

| Секция | Назначение |
|---|---|
| `launcher.python` | Python подготовленного окружения; по умолчанию `.venv/bin/python`. Main сам переключается на него, без активации venv в терминале. |
| `api.host`, `api.port` | Адрес прослушивания FastAPI. |
| `api.frontend_origin` | Публичный origin фронта для CORS и ссылок подтверждения: схема, хост и порт, без пути. |
| `database.dsn` | Строка PostgreSQL URI или libpq conninfo; обязательна. |
| `database.ready_timeout_seconds`, `connect_timeout_seconds`, `retry_seconds` | Общий срок ожидания БД, предел попытки и интервал повторения. |
| `models.generation`, `embedding`, `ocr`, `handwriting` | GGUF генерации, каталог E5, каталог OCR и необязательная отдельная GGUF для рукописей. |
| `storage.originals` | Каталог оригиналов; относительный путь отсчитывается от backend. |
| `smtp` | Хост, порт, отправитель, режим TLS, учётные данные и timeout. Пустые host/sender оставляют отправку почты ненастроенной. |
| `smtp.ports` | Порты по режимам TLS для отдельно запускаемых компонентов без явной SMTP-переменной порта. |
| `supervisor` | Интервал контроля, время штатной остановки и время ожидания после принудительной остановки. |

Пароли и DSN задавайте только в локальном файле с ограниченным доступом. Launcher не выводит их значения. Не размещайте секреты в общих конфигах и шаблонах. Альтернативные файлы вне стандартного локального пути оператор также должен держать вне Git.

Профили моделей и их контрольные суммы остаются в `backend/config/ocr.toml`, настройки генерации/embedding — в `runtime.toml`, лимиты документов — в `documents.toml`. Это отдельные существующие владельцы настроек. Административные overrides сохраняются в БД.

### Фронтенд

| Ключ | Назначение |
|---|---|
| `server.host`, `server.port` | Адрес HTTP-сервера интерфейса. |
| `server.poll_seconds` | Интервал обработки остановки сервера. |
| `api.origin` | Адрес API, к которому обращается браузер; без `/api` и других путей. |
| `client.reconnect_ms` | Пауза перед повторным подключением к потоку событий. |

Порт `0` фронта допускает выбор свободного порта ОС; фактический адрес отображается при старте. Для обычной работы задавайте фиксированный порт, согласованный с `api.frontend_origin` бэка.

Браузер получает публичные `api.origin`, `client.reconnect_ms` и параметры `ui`, подставленные в HTML. Сервер разрешает index и JS/CSS из `src/`; конфиги, Python-код, обходы каталогов и symlink-пути не раздаются. При внешнем размещении статических файлов сервер развёртывания должен аналогично подставить публичные значения в соответствующие `__RAG_*__` placeholders из `frontend/index.html`.

## Поведение запуска и диагностика

Бэк проверяет Python и зависимости до импортов приложения, затем конфиг, полный manifest моделей и совместимость runtime, ждёт PostgreSQL, затем запускает documents, generation и API отдельными группами процессов. Сообщение `Backend started` означает создание процесса, а не готовность модели. Uvicorn начинает слушать после своего startup; generation становится доступной после загрузки модели и обновления существующего lease. OCR загружается при обработке документа.

При ошибке параметров исправьте ключ, указанный в диагностике. При недоступной БД проверьте DSN, сеть и состояние PostgreSQL. Занятый API-порт приводит к завершению API и остановке остальных компонентов. При занятом порте фронта main завершается с ошибкой. Launcher рассчитан на Linux, как и существующий generation supervisor с host fence.

## Технические проверки

Проверки находятся в `backend/tests/test_launch_configuration.py`, `test_backend_launcher.py`, `test_frontend_launcher.py`, `test_model_artifacts.py` и `test_startup_bootstrap.py`. Они используют реальные HTTP-сокеты, процессы и временный PostgreSQL. Проверка полного бэкендового main дополнительно требует `RAG_MODEL_PATH`, `RAG_E5_DIR`, `RAG_OCR_DIR`, указывающих на подготовленные модели; без них этот отдельный smoke пропускается. Проверки качества ответов модели не являются проверками запуска.
