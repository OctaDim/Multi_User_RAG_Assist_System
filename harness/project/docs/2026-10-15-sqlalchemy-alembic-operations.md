# Работа с SQLAlchemy и Alembic

Дата: 2026-10-15. Реализация и техническая проверка завершены; границы проверки перечислены ниже.

## Модели и операции приложения

Модели расположены в `backend/app/models/`, по одной таблице на Python-модуль. Общая Base и явный реестр импортов предоставляют metadata для Alembic. Импорт моделей не подключается к PostgreSQL и не выполняет DDL.

`app.db.Database` владеет async engine и фабрикой сессий. Создавайте один экземпляр на процесс и его event loop. `database.session()` предоставляет отдельную AsyncSession операции и закрывает её; commit задаётся явно через `async with session.begin()`. Вложенные запросы получают ту же сессию. Не разделяйте одну сессию между конкурентными задачами. При завершении процесса вызывайте `await database.dispose()` после остановки фоновых задач.

Запросы приложения строятся SQLAlchemy expressions в существующих доменных модулях; общие части SELECT выделяются в небольшие функции. Штатный AsyncPostgresSaver получает соединение текущей транзакции после проверок доступа; его внутренний SQL остаётся кодом сторонней библиотеки.

## Подготовка и обновление базы

Строка подключения передаётся существующей переменной `RAG_DATABASE_URL`; поддерживаются PostgreSQL URI и libpq conninfo. Из корня репозитория:

```sh
uv run --project backend --frozen alembic -c backend/alembic.ini upgrade head
```

Эквивалентная команда приложения, работающая также из установленного wheel:

```sh
uv run --project backend --frozen rag-migrate
```

Перед первым переходом остановите старые API и воркеры: migration lock сериализует миграторы, но не блокирует бизнес-запросы старых процессов. Пустая БД проходит всю цепочку Alembic. Для старой БД проверяются прежний журнал, контрольные суммы и соответствующая схема; после подтверждения уже выполненная часть отмечается соответствующей ревизией Alembic, затем выполняется остаток цепочки. Данные выполненных этапов не переигрываются.

Ревизии 0001–0006 воспроизводят все прежние этапы приложения, 0007 управляет checkpoint-схемой saver 3.1.3. `lifecycle_migrations` существующей установки сохраняется для истории; новые изменения учитываются только в `alembic_version`. Старые SQL находятся лишь в `backend/tests/fixtures/legacy_migrations/` для воспроизводимых проверок принятия прежней БД.

Если известная схема повреждена, подготовка завершается ошибкой с описанием несовпадения. Она не создаёт замену утраченной таблице и не скрывает потерю данных. Offline adoption и разрушительный downgrade начальной истории не поддерживаются.

## Следующее изменение модели

1. Измените соответствующий модуль модели.
2. На отдельной проверочной БД, соответствующей текущей ревизии, подготовьте ревизию:

   ```sh
   uv run --project backend --frozen alembic -c backend/alembic.ini revision --autogenerate -m "describe schema change"
   ```

3. Проверьте созданные операции и перенос данных вручную. Alembic не выводит автоматически все изменения view/function/trigger и CHECK-ограничений.
4. Подготовьте `backend/migrations/contracts/<revision>.json`: скопируйте контракт предыдущей ревизии и внесите ожидаемые изменения объектов. Старые контракты сохраняйте неизменными. Для большого изменения можно получить кандидат снимка в disposable БД через `schema_contract.snapshot`, применив отдельную ревизию в `Operations.context`; такой кандидат тоже требует проверки.
5. Проверьте переход с предыдущей ревизии, пустую БД, сохранение данных и повторный `upgrade head`. Команда `alembic ... check` проверяет расхождения прикладной metadata; checkpoint и служебные журналы исключены из autogenerate.
6. Сохраните модель, подготовленную ревизию, её контракт и технические проверки одним согласованным изменением.

При запуске приложения выполняется upgrade подготовленных ревизий. Генерация новых ревизий при запуске не выполняется; `create_all()` и runtime `AsyncPostgresSaver.setup()` не используются.

Проверка качества 30/30 ответов и цитат исключена пользователем из текущей задачи. Технические проверки авторизации и целостности источников этим исключением не отменены.

## Результаты проверки и открытые ограничения

Миграции, модели, атомарность checkpoint, независимые сессии, обработка ошибок соединения, запуск API/воркеров и установленный wheel проверены на временной PostgreSQL. Подробные команды, результаты и прежние ошибки сохранены в [отчёте проверки](../testing/evidence/work/2026-10-15-sqlalchemy-alembic.md).

Все 319 первоначально выбранных технических сценариев имеют успешный результат в совокупности отдельных запусков. Это не единый чистый прогон всей системы. После согласованного пользователем увеличения тестовых ожиданий оба сценария удаления источника прошли. После установки печатному OCR контекста 16384 прошли также паспорт PDF и полный многостраничный PDF: **2 passed за 1042.48 s**. Последний распознал 15 страниц, подтвердил управляемый отказ страницы 16, исключение повреждённого файла из поиска и ответ по исправному соседнему документу. Команды, исходные результаты и последующая проверка разбиения сохранены в [новом отчёте](../testing/evidence/work/2026-10-15-ocr-context-and-fragments.md).

После реализации разбиения дополнительный паспорт PDF вновь не прошёл: запрос принят HTTP 200, затем supervisor потерял владение координатором. Пользователь отдельно разрешил убрать из supervisor тяжёлые inference-импорты: они перенесены в native worker. Проверки владения/восстановления/планировщика/RAG/native прошли (**46 passed**), память свежего импорта supervisor снизилась 142228→67988 KiB. Повтор обоих PDF с этой правкой завершился успешно: **2 passed за 963.69 s**, включая все 15 OCR-страниц и ответ по соседнему источнику. Результаты и пределы измерений — в [отчёте supervisor](../testing/evidence/work/2026-10-15-light-supervisor.md).

Итоговая коллекция: 338 технических сценариев и один исключённый quality30. Каждый технический сценарий имеет успешный результат в совокупности описанных запусков; вся коллекция единым чистым прогоном не выполнялась. Дополнительные проверки OCR/геометрии/публикации и установленного wheel прошли. Код сохранён локально в `4398854` и `ab0d15f` поверх уже выполненных U1–U3; рабочая БД не мигрировалась.

Ранее supervisor терял владение координатором, а запрос генерации получал HTTP 503. Сравнение с кодом до переноса также воспроизвело потерю владения. [Диагностика причины](../testing/evidence/work/2026-10-15-coordinator-ownership-root-cause.md) непосредственно зафиксировала page-in supervisor дольше lease, при этом PostgreSQL ждал клиента после BEGIN; также измерена длительная полная GC с массовыми faults. Один успешный повтор не доказывает устранение всех возможных сбоев при нехватке памяти. Прежний прогон четырёх сценариев и его исходные журналы сохранены в [дополнении к отчёту](../testing/evidence/work/2026-10-15-sqlalchemy-timeout-repeat.md).

При сравнении настройки пула и защитные таймауты приложения не менялись. Этот отчёт не служит основанием объявлять проверку пройденной или увеличивать lease в работающем сервисе. Рабочая БД не изменялась.

Тестовые ожидания: OCR 300 секунд, появление ответа 120 секунд, завершение 180 секунд, многостраничный PDF 2000 секунд. Параметры приложения: владение координатором 5 секунд, связь вкладки 15 секунд и отсрочка 10 секунд. Пулы и GC в рамках исправления не менялись.

Печатный профиль в `backend/config/ocr.toml` использует контекст 16384, рукописный — 4096. Изображения крупнее 2400 пикселей делятся перед детектором и OCR на фрагменты до 2400×2400 с перекрытием 128; где возможно, границы сдвигаются в пустые промежутки. Модели обрабатывают фрагменты последовательно. Маски всех найденных рукописных областей применяются до печатного OCR; запреты и отзыв доступа сохраняются. Прямоугольники, полигоны и вложенные детекции возвращаются в координаты исходной страницы, повторы убираются по геометрии. Ошибка фрагмента прерывает всю страницу; частичный текст страницы не публикуется. Исходное изображение и его маски всё ещё находятся в памяти: разбиение ограничивает вход модели, но не превращает загрузку растров в потоковую.
