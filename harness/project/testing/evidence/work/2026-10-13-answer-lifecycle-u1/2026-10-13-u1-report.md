## Native proof — G1

Команда:

```sh
RAG_MODEL_PATH=/tmp/rag-answer-lifecycle-models/Qwen3.5-2B-Q4_K_M.gguf uv run --project backend --frozen --cache-dir /tmp/rag-answer-lifecycle-uv-cache pytest -c backend/pyproject.toml backend/tests/runtime/test_generation_contract.py -q -s
```

[Исходный результат](native-proof-v1.txt): 2 passed, 39.39 секунд.
[Сборка и hashes библиотек](environment-v1.json): Python 3.12.15,
llama-cpp-python 0.3.36, CPU; модель Unsloth Qwen3.5-2B Q4_K_M из ревизии
`f6d5376be1edb4d416d56da11e5397a961aca8ae`, SHA256 соответствует импортированному
manifest прежних проб. Загрузка и установка: [модель](model-download-v1.txt),
[bindings через uv](native-install-v1.txt).

В одной native модели одновременно созданы 12 разных contexts с отдельными
samplers и n_ctx=4096; тринадцатый запрос ждёт. Реальные prefill/decode calls
и token IDs сохраняются в trace. Для каждого вопроса получен отдельный контрольный
prefix; interleaved выдача совпала с ним. Полный round-robin круг обслуживает
все runnable contexts. Ширина шага менялась 3→2→4; лимит активных — 12→6→12.
Уменьшение при десяти активных не удаляет их; ожидающий допускается после
освобождения до пяти. Сохранённые активные contexts при повышении лимита
сохраняют native pointers. Отдельно проверены EOS, освобождение context и
продолжение соседнего запроса.

Это доказательство возможностей выбранной сборки для тестовых prompts;
production scheduler, PostgreSQL settings revisions, полный контекст 4096 токенов
и совместная нагрузка OCR/API/DB проверяются последующими units. Здесь revision
является revision тестового управляющего цикла, а не записью ещё не созданной БД.
Численного SLA и доказательства приёмки всего MVP этот результат не даёт.
Пиковый RSS тестового процесса в trace: 3 019 456 KiB (около 2,88 GiB).

## Browser proof — G2

Команда:

```sh
xvfb-run -a uv run --project backend --frozen --cache-dir /tmp/rag-answer-lifecycle-uv-cache pytest -c backend/pyproject.toml backend/tests/browser/test_draft_lifecycle.py -q -s
```

[Текущий исходный результат](browser-proof-v5.txt): 6 passed, 10.05 секунд.
Проверялся настоящий Chromium 131.0.6778.33, Playwright 1.49.1, отдельные
временные профили под Xvfb. Расширение стенда вызывает browser-native
`chrome.sessions.restore` и `chrome.tabs.duplicate`; storage не подставляется
из теста. Перезапуск проверяется с native `--restore-last-session`.

Reload сохраняет отдельные черновики бесед и вкладок и ту же tab identity.
Новая вкладка, восстановление закрытой вкладки, opener, duplicate и восстановление
после перезапуска не возвращают старый текст. При закрытии/restore проверены
обе беседы; соседняя открытая вкладка сохраняет свой черновик.
Opener и duplicate получают другую tab identity. Серверный presence/proof
проверяется в U5/U8, а не подменяется этой browser identity.

Простой sessionStorage-кандидат был опровергнут: [browser-proof-v3.txt](browser-proof-v3.txt)
содержит 2 passed / 2 failed — restore возвращал закрытый черновик, opener его
копировал. Уточнённый кандидат очищает storage при загрузке документа, если
navigation type отличается от reload. В проверенных restore/duplicate случаях
Chromium сообщает back_forward. [browser-proof-v4.txt](browser-proof-v4.txt)
содержит первый успешный прогон уточнённого кандидата. Другие браузеры не
запускались; результат Chromium не является доказательством для всех платформ.
Запрет восстановления R27 не ослаблен и не заменён исключением.

[browser-proof-v1.txt](browser-proof-v1.txt) — ошибка ограничения socket sandbox;
[browser-proof-v2.txt](browser-proof-v2.txt) — ошибка получения browser version
в стенде, исправленная до продуктовых assertions. Эти запуски не доказывают
поведение продукта. Socket/browser запуск разрешён через расширение sandbox.

Исходные логи сохранены без изменения whitespace. Общий `git diff --cached --check`
сообщает о trailing spaces, напечатанных pytest/native logger в raw logs;
их очистка нарушила бы неизменность исходных свидетельств. Проверка whitespace
прикладных исходников, lockfile, отчёта и JSON выполняется отдельно.
