# Контекст печатного OCR и разбиение длинных изображений

Создано: 2026-10-15. Этап завершён: разбиение реализовано и проверено;
заключительный браузерный паспорт не прошёл из-за потери владения supervisor.
Обычный отчёт приложения, не свидетельство механизма harness.

Пользователь поручил установить печатному OCR контекст 16384 и повторить
два падения: паспорт ответа по PDF и whole-pdf многостраничного документа.
Изменён только `backend/config/ocr.toml`, handwriting сохраняет 4096.
Прежние результаты и первопричина сохранены отдельно:
[повтор четырёх тестов](2026-10-15-sqlalchemy-timeout-repeat.md),
[диагностика владения координатором](2026-10-15-coordinator-ownership-root-cause.md).
Уменьшение контекста не считается доказанным устранением всех сбоев памяти.

Исходный повтор двух тестов выполнен без диагностических плагинов и изменения GC:
`/tmp/rag-printed-16384-repeat-20261015.log`,
`/tmp/rag-printed-16384-repeat-20261015.xml`,
`/tmp/rag-printed-16384-repeat-20261015/`.
Оба сценария прошли: **2 passed in 1042.48s (0:17:22)**.
Паспорт: 160.767 s; whole-pdf: 881.059 s. Whole-pdf подтвердил 15 настоящих
native OCR-страниц, управляемый отказ страницы 16, отсутствие повреждённого
источника в поиске и паспорте, а также ответ по исправному соседнему документу.
Продуктовый код OCR до завершения этого прогона не менялся.
Сохранены [pytest log](2026-10-15-ocr-context-16384-repeat.pytest.log)
и [JUnit](2026-10-15-ocr-context-16384-repeat.junit.xml).

Во время прогона пользователь поручил предварительно разделять длинные изображения.
Короткий дизайн в чате явно подтверждён ответом «Да, реализовать этот дизайн»:

- фрагменты до 2400 пикселей по каждой стороне, перекрытие 128 пикселей;
- разбиение перед детектором и OCR, по возможности в свободных промежутках;
- последовательная обработка существующими моделями;
- координаты прямоугольников, полигонов и вложенных детекций возвращаются на исходную страницу;
- повторы определяются геометрией, одинаковый текст в разных местах сохраняется;
- печатный OCR получает изображение с масками всех обнаруженных рукописных областей;
- результат страницы возвращается только после успешной обработки всех фрагментов;
- ошибки и отмена не разрешают частичную публикацию;
- существующие разрешения на рукопись и обычный путь коротких страниц сохраняются.

Разбиение и геометрия реализованы в `backend/app/ocr_fragments.py`, подключены
в `DocumentOCR.prepare_image` и `finish_page`. Обычный путь до 2400 пикселей
сохранён. Детекции объединяются до маскирования; печатные фрагменты вызываются
последовательно, пустые пропускаются. Вызов завершается только после всех
фрагментов и проверки отмены. Тест с настоящими API/worker/БД подтвердил, что
ошибка второго OCR-фрагмента оставляет `ready=false`, `published_revision=NULL`,
`error=ocr_truncated`, `failure_page=1`, без `document_page_texts` и `source_chunks`;
исходный файл доступен владельцу, документ для поиска недоступен.

Первый расширенный native-прогон был запущен внутри сетевой песочницы и завис
на существующей проверке отмены. Снят стек (процесс завершён SIGABRT, core limit 0).
В стеке — тестовый HeldCancellation.release.wait, главный поток ждёт epoll.
Диагностический повтор с трассировкой показал, что entered установлен, но event
loop не получает уведомление. Минимальная проверка без OCR подтвердила:
`socket.socketpair().send()` получает EPERM внутри песочницы;
`asyncio.wait_for(asyncio.to_thread(delayed_0_1s),1)` заканчивается TimeoutError.
В разрешённом локальном режиме тот же пример завершился за 0.1019 s, send успешен.
Код приложения/тестов отмены для обхода не менялся. Новый plain-прогон вне
этого ограничения прошёл все 18 существующих OCR-тестов и новый native-тест:
**19 passed in 113.26s (0:01:53)**. Прерванные прогоны успешными не считаются.
