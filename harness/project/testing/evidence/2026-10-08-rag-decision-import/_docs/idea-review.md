# Повторная проверка идеи

Дата: 2026-10-03. Статус: продуктовые решения согласованы, повторная проверка идеи завершена. Источники текущих решений: [архитектура](architecture.md), [проверка моделей](local-ai.md). Реализация и приёмочные испытания портала ещё не выполнены; технические кандидаты не выдаются за утверждённые зависимости.

## Задача пользователя

Как помочь человеку получать проверяемые ответы по собственной библиотеке документов и продолжать диалог, сохраняя приватность материалов и возможность пользоваться разными интерфейсами?

Подтверждённый продукт: портал для 30 пользователей, до 10 одновременно, с личными документами, пакетной загрузкой, OCR, чатом и внутренней админкой через API. Целевой пользователь работает со своей библиотекой PDF, DOCX, TXT и Markdown; начальный предел — 1000 документов и 2 ГБ оригиналов на пользователя. Наличие чата само по себе не доказывает преимущество перед ручным поиском: проверяем, помогает ли ответ с источниками быстрее решать задачу пользователя.

## Принятое направление

Гибридный монолит: независимые `backend/` и `frontend/`, async FastAPI, отдельный worker, файловое хранилище, PostgreSQL/pgvector. В backend работает LangGraph, состояние бесед сохраняет `AsyncPostgresSaver`. Проверка владельца обязательна независимо от `thread_id`.

Локальный MVP: E5 ONNX INT8 через ONNX Runtime CPU; Qwen3.5-2B GGUF Q4_K_M через llama.cpp CPU, контекст запроса 4096, thinking выключен. По умолчанию 3 одновременные асинхронные генерации на сервис, остальные в очередь; лимит задаётся отдельным конфигурационным файлом и применяется при запуске. Регистрация самостоятельная, email/пароль с подтверждением email; административная блокировка независима от будущей оплаты. Роли: пользователь, администратор, super-admin; только последнему разрешено административное чтение документов и переписок других пользователей. Проверка GLM отложена пользователем до необходимости fallback.

### Правила сценария и уточнения для реализации

Ниже согласованные правила и рекомендации по их реализации в пограничных ситуациях. Уточнения реализации не означают, что портал уже построен или проверен.

| Ситуация | Предлагаемое поведение MVP |
| --- | --- |
| Новый документ и существующая беседа | Беседа «вся библиотека» видит новые готовые документы со следующего вопроса. Беседа с выбранными документами сохраняет выбранную область. Старые ответы автоматически не пересчитываются. |
| Повторная загрузка и замена | Повтор HTTP-запроса одной операции не создаёт второй документ. Отдельная явная загрузка считается новым документом, даже при одинаковом имени. Версионирование и автоматическое слияние не входят в MVP; пользователь удаляет ненужную копию. |
| Обработка завершилась лишь для части пачки | Готовые документы доступны для поиска; для остальных видны состояния и причины ошибок. UI предупреждает, что часть выбранной библиотеки ещё не готова. |
| Все выбранные документы недоступны | Показать, что готовых источников нет. Не расширять область поиска автоматически и не выдавать общий ответ модели за ответ по документам. |
| Заняты все места генерации | Подтверждено: по умолчанию 3 параллельные генерации, остальные в очередь; лимит применяется из отдельного файла при запуске. Предлагается показывать ожидание и позволять отмену; предел очереди и ожидания ещё определяется. Индексация не должна бесконтрольно занимать все CPU одновременно с чатом. |
| Обрыв вкладки или соединения | Принятый запрос имеет сохранённый статус. Повторное открытие беседы показывает статус или готовый ответ; повтор отправки с тем же ID не добавляет новый пользовательский вопрос. Явная отмена отличается от закрытия вкладки. |
| Аккаунт мягко удалён или административно отключён | Подтверждено: новые защищённые операции запрещены, дальнейшая выдача потока прекращается; уже доставленный текст отозвать нельзя. Проверяются все действующие состояния доступа, в том числе для очереди и перед публикацией результата. Обработка останавливается на безопасной границе, данные сохраняются. В MVP оплата на доступ не влияет. |
| Удаление документа пересекается с генерацией | Отметить документ удалённым сразу; не публиковать готовый ответ, если его источники потеряли доступ до публикации. Прекратить дальнейшую выдачу потока, если она уже началась. Очистить затронутые checkpoints и начать новый контекст согласно выбранной пользователем политике истории. |
| Удаление аккаунта | Подтверждено: только `active=False`, без физической очистки данных. Мягкое удаление имеет приоритет над административным отключением и оплатой; изменение этих полей не восстанавливает аккаунт. |
| Резервные копии | Подтверждена ежедневная согласованная копия БД и оригиналов, хранение 7 дней. Удалённые отдельные документы могут оставаться в закрытых копиях до ротации; мягко удалённые аккаунты сохраняют данные. Перед открытием восстановленного сервиса применяются последующие удаления и ограничения доступа. Для MVP выбрана `_RESERVED_COPIES/` на том же диске в корне проекта, исключённая из Git вместе с содержимым. Ограничение: копии не защищают от отказа этого диска. |
| Источники в ответе | Ссылка открывает доступный документ и использованный фрагмент; для PDF указывается страница, если извлечение сохраняет её достоверно. Выдуманные моделью идентификаторы источников не принимаются. При нехватке оснований ответ сообщает о недостатке найденных сведений. |

Пользователь подтвердил постепенную выдачу текста и кнопку остановки в MVP. Для передачи используется HTTP API/SSE; остановка отменяет серверную генерацию, а не только закрывает отображение. Прерванный текст помечается и не считается завершённым ответом. Пользовательская история хранится независимо от транспортного соединения. Проверка доступа перед публикацией и отзыв доступа во время потока — отдельные обязанности backend; выбор SSE их не реализует автоматически.

### Как принимать MVP

Набор проверки для реализации: реальные документы первых пользователей, фактические вопросы с заранее отмеченными источниками, вопросы без оснований, уточнения с историей, удаление источника, блокировка во время запроса, перезапуск worker и двухпользовательская проверка изоляции. Документирование набора и порогов закрывает решение о приёмке; успешное выполнение проверок требуется уже при реализации.

Для прав доступа критерий однозначный: ни один запрещённый сценарий не должен вернуть содержимое другого пользователя. Разрешённое чтение super-admin проверяется как положительный сценарий, отдельно от личного RAG:

| Сценарий | Ожидаемый результат по принятым решениям |
| --- | --- |
| Пользователь открывает свой документ или беседу | Доступ при отсутствии мягкого удаления и административного отключения, с подтверждённым email. В MVP значение `paid` не влияет на результат. |
| Пользователь подставляет чужой document_id или thread_id | Содержимое не выдаётся; запуск, история, источники, скачивание и возобновление проверяют права отдельно. |
| Обычный администратор читает чужой документ или переписку | Запрет, включая обход через фрагменты, экспорт, диагностику и checkpoint. |
| Super-admin читает чужой документ или переписку через административный API | Разрешено при действующих полномочиях; чтение фиксируется в аудите без копирования содержимого. |
| Super-admin задаёт вопрос в своём личном чате | Чужие библиотеки не добавляются к RAG автоматически из-за роли. |
| Роль super-admin отозвана | Последующие административные чтения запрещены; сохранённая сессия не сохраняет прежние полномочия. |
| Мягко удалённому аккаунту меняют `disabled` или `paid` | Доступ не восстанавливается, пока `active=False`. |
| В MVP меняют только `paid` | Доступ и текущие операции не меняются: проверка оплаты отключена. |

Допуск по состояниям аккаунта в MVP: `active=True AND disabled=True`; после подключения биллинга добавляется `AND paid=True`. Значение `disabled=False` блокирует по прямому указанию пользователя, несмотря на имя поля. Эти условия не заменяют аутентификацию, проверку email, роли и владельца ресурса.

Для генерации проверяется запуск десяти независимых запросов: одновременно исполняется не более трёх, остальные ожидают; свободное место получает следующий запрос. Отдельно проверяются значения конфигурации 1 и 3 после перезапуска, отклонение некорректного значения, отсутствие умножения лимита при нескольких API-процессах и освобождение места после ошибки/отмены. Это критерии будущей реализации, не выполненные тесты.

Пользователь установил обязательный порог качества: **30 корректных результатов из 30** заранее подготовленных вопросов по реальным документам. Допустимого числа неверных результатов нет. Набор включает вопросы с ответами и ожидаемыми источниками, отсутствие сведений и уточнения с историей. Корректный результат — фактически верный ответ с поддерживающим источником либо обоснованное сообщение о нехватке сведений для соответствующего контрольного вопроса. Набор и ожидаемые ответы фиксируются до прогона, а не подстраиваются под результат. При ошибке MVP не проходит этот критерий; после исправления повторяется весь набор. Это утверждённое требование, а не измеренное качество или гарантия для произвольных документов.

Проверки прав, удаления и очереди должны пройти полностью, отдельно от проверки 30 вопросов. Задержки измеряются для совместного сервиса с OCR при 10 пользователях и лимите 3 генерации, отдельно время в очереди, до первого текста и до завершения. Численный предел времени заранее не обещается. Проверка восстановления должна подтвердить согласованность файлов и БД, а также отсутствие возврата ранее удалённых данных в доступный сервис.

### Согласование завершено

Начальные лимиты, место резервных копий `_RESERVED_COPIES/`, срок 7 дней, ежедневное создание копий, потоковый показ ответа с остановкой, личные библиотеки и порог 30 из 30 согласованы. Неотвеченных продуктовых вопросов текущей проверки не осталось. Если возникнут новые вопросы, они задаются по одному по просьбе пользователя.

Учётные данные отправки email — параметры развёртывания, а не новая продуктовая развилка. Выбор библиотеки аккаунтов, очереди, OCR/парсеров и frontend остаётся отдельной задачей технического проектирования; проверка идеи не выдаётся за завершение этой задачи.

## Допущения и проверка

- **Качество:** локальная модель справится с реальными материалами. Пока проверены только малые синтетические сценарии. Проверка — согласованный набор реальных документов и контрольных вопросов; отдельно оцениваются поиск и генерация.
- **Память и нагрузка:** WSL с 5,6 GiB вместит весь сервис, а не только модели. Проверка — совместный запуск PostgreSQL, API, worker, embeddings и LLM; наблюдение RAM, swap, очереди и задержек при выбранной нагрузке. Существующий замер моделей этого не доказывает.
- **Контекст:** 4096 токенов хватит для источников, истории и ответа. Проверка — диалоги с уточнениями и несколькими источниками; полная история хранится отдельно от окна модели.
- **Ценность:** ответы с цитатами помогают первым пользователям быстрее находить нужные сведения. Проверка — их реальные задачи и сопоставление с ручным поиском; технический стек сам по себе не является ценностью продукта.

Эти допущения нельзя закрыть решением на бумаге. Закрывается способ проверки и критерий принятия; фактическое подтверждение относится к реализации MVP.

## Границы MVP

Уже включены: аккаунты, личная библиотека и пакетная загрузка, фоновые статусы, приватный RAG-чат с историей, API, админка, локальные модели. Предлагается также включить ссылки на источники, удаление данных и восстановление после сбоев как часть целостного пользовательского сценария.

Не реализуем сейчас: биллинг и проверку `paid`, физическое удаление аккаунта со всеми данными, PWA и мессенджеры, платные модели, автоматический внешний fallback. Отсутствие организаций, команд, общих папок и обмена документами в MVP подтверждено пользователем. Автономные действия агента, web-поиск и междиалоговая персональная память не следуют из текущего запроса и предлагаются вне MVP. OCR включён пользователем в MVP; его нагрузка должна учитываться вместе с RAG.

Выбор frontend-фреймворка, драйвера PostgreSQL, библиотеки аккаунтов и механизма очереди относится к следующему техническому решению. Они не должны скрывать нерешённые правила доступа, удаления или нагрузки. Текущий документ не утверждает их за пользователя.
